# 产品形态设计

## 一、设计结论

本项目最终采用的产品形态是：

**APP 每次进入 AI 导购时默认创建一段新的导购会话；用户可以从历史会话中手动继续之前的购物任务；同一会话内部保留短期上下文和任务记忆，但不同会话之间不默认继承上下文。**

这个设计不是因为“导购 Agent 会多次搜索，而问答 Agent 不会”。这个理由并不成立：导购 Agent 确实可能多次搜索商品、评价、知识库和买手经验，问答 Agent 也可能每次查询不同资料。两类 Agent 的关键差异不在于搜索次数，而在于：

1. **电商导购是任务型场景**：一次会话通常围绕一个明确购物任务展开，例如“买洗面奶”“挑耳机”“给妈妈买礼物”。
2. **电商导购是交易型场景**：导购结果可能继续触发加入购物车、结算、支付、查看订单等真实业务动作。
3. **电商导购强依赖商品事实**：推荐理由、价格、库存、优惠、订单状态等必须来自当前工具和业务数据，不能被历史闲聊内容污染。
4. **电商导购需要清晰责任边界**：用户需要知道当前推荐、加购和结算是基于哪一次购物任务产生的。

因此，本系统不采用“默认永远继承上一段对话”的形态，而采用“默认新任务、历史可恢复、任务内有记忆”的形态。

## 二、项目中曾考虑的两种产品形态

### 方案 A：持续继承上一段对话

这种形态类似一些通用对话助手：用户再次打开应用时，系统默认沿用上一次对话，模型会自然继承之前所有上下文。

优点是连续性强，用户可以直接说“继续”“刚才那个”“第二个不错”，系统更容易接上上一轮话题。

但在电商场景中，这种方式存在明显风险：

1. **容易混淆不同购物任务**  
   用户昨天在看洗面奶，今天打开 APP 想买耳机。如果系统默认继承昨天的洗面奶上下文，AI 可能错误地把旧偏好、旧商品、旧预算带入今天的新需求。

2. **交易动作存在误触发风险**  
   后端已经支持购物车、订单、优惠券、评价等真实业务工具。用户说“把第二个加入购物车”时，系统必须明确“第二个”来自当前任务，而不是来自几天前的历史推荐。

3. **导购结果难以解释和追溯**  
   如果模型混入过多历史上下文，用户很难判断本次推荐到底基于当前需求、旧偏好，还是历史对话里的某个临时条件。

4. **不利于管理会话历史**  
   电商任务天然适合按主题归档，例如“通勤耳机推荐”“敏感肌洗面奶”“露营装备清单”。如果所有内容都塞进一条长对话，后续查找和复盘成本会变高。

### 方案 B：默认新开会话，历史会话可继续

这种形态类似 ChatGPT 的会话组织方式：新的问题默认进入新会话，但用户可以从历史列表中回到某个具体会话继续。

在电商导购场景中，这种方式更适合：

1. **每个会话对应一个购物任务**  
   一个会话可以围绕一个购物目标持续展开，例如需求分析、商品搜索、对比推荐、加入购物车、结算确认。

2. **任务内上下文保持连续**  
   在同一个会话中，用户可以自然追问“便宜一点的呢”“第二个加入购物车”“看看评价”。后端会通过会话内短期记忆和商品 ID 引用，帮助 Agent 理解这些省略表达。

3. **任务间上下文默认隔离**  
   当用户开始新的购物任务时，不自动继承上一段会话，避免旧商品、旧预算、旧意图影响当前判断。

4. **历史任务可以恢复**  
   用户如果确实想继续之前的购物任务，可以从历史会话中打开对应记录，继续沿用那段会话的上下文。

因此，本项目选择方案 B。

## 三、后端架构对该产品形态的支撑

当前后端并不是一个简单的“把用户问题发给大模型”的聊天系统，而是围绕电商导购任务设计了一套完整的 Agent 运行链路。

### 1. 会话模型支撑“一个会话一个购物任务”

后端有独立的会话、用户消息、Agent Run 和 Trace 数据结构：

- `chat_sessions`：记录会话标题、摘要、消息数量、最后消息时间、置顶状态、删除状态。
- `user_messages`：记录用户在某个会话里的问题和附件。
- `agent_runs`：记录每次 Agent 运行的状态、回答内容、结构化卡片、追问建议等。
- `agent_trace_events`：记录 Agent 运行过程中的路由、工具调用、耗时和错误信息。

这说明产品形态上应当把“会话”设计成一个可管理的购物任务容器，而不是只有一条无限延长的对话流。

### 2. Agent 路由支撑“导购任务”和“服务任务”分流

后端会先判断用户请求属于：

- `guide`：导购类请求，例如选品、对比、搭配、场景方案、商品详情、图片找同款。
- `non_guide`：非导购服务类请求，例如购物车、订单、优惠券、评价、售后、账号、闲聊等。

导购类请求会继续细分为：

- P1 商品深度咨询
- P2 多商品对比决策
- P3 穿搭 / 搭配
- P4 品类选购
- P5 场景方案
- P6 开放探索

非导购类请求会继续细分为购物车、订单、优惠券、评价、售后、账号、导航等服务域。

这意味着一次 AI 对话并不只是“聊天”，而是在判断当前任务应该进入哪条业务链路。默认新会话可以让每次路由更聚焦，减少历史上下文对当前意图判断的干扰。

### 3. 工具权限支撑“当前任务内可控执行”

后端为不同意图配置了不同工具权限。例如：

- 导购意图可以使用商品搜索、图片搜同款、知识库搜索等工具。
- 购物车意图可以读取购物车、添加商品、修改数量、删除商品。
- 订单意图可以查看订单、支付订单、取消订单、确认收货。
- 优惠券意图可以查看、领取、试算优惠。
- 评价意图可以查看或创建商品评价。

同时，后端会限制不相关工具，避免模型在错误意图下调用高风险动作。

这进一步说明：当前会话应该对应当前任务。因为工具权限、业务动作和回答策略都跟当前任务强相关。如果默认继承太多旧上下文，模型可能把旧任务里的商品引用带入新任务，从而影响工具调用的准确性。

### 4. 确定性交易动作支撑“安全闭环”

对于加入购物车、结算等关键动作，后端不是完全依赖大模型自由生成，而是通过确定性逻辑执行：

- 加购必须能明确商品 ID。
- 商品不明确时需要追问，不能猜。
- 结算必须读取当前购物车并真实生成订单。
- 回答中展示的商品卡片必须来自工具返回的可信商品 ID。

这种设计让系统可以完成真实交易闭环，也提高了对上下文边界的要求。用户说“加入购物车”时，系统必须明确这是本次会话里的哪个商品，而不是历史对话里的某个商品。

### 5. 短期记忆支撑“任务内连续追问”

后端已经实现会话内短期记忆能力，会在当前账号、当前会话范围内读取近期消息，并判断是否与当前问题直接相关。

例如用户在同一会话中说：

- “第二个加入购物车”
- “刚才那个有没有评价？”
- “便宜一点的还有吗？”
- “继续推荐”

系统可以利用当前会话内的商品引用和摘要来理解这些表达。

但记忆检索策略不是把所有历史都塞给模型，而是只选取与当前问题直接相关的内容。这样既能保证同一购物任务内的连续性，又能避免跨任务上下文污染。

这正好对应产品形态上的设计：**不是没有记忆，而是有边界的记忆；不是永远继承，而是任务内继承。**

## 四、为什么最终采用“默认新会话 + 历史可继续”

### 1. 更符合用户真实购物心智

用户每次打开电商 APP，通常不是为了继续一个长期话题，而是为了解决一个具体购物问题：

- 今天想买一瓶洗面奶。
- 明天想挑一副耳机。
- 周末想买露营装备。
- 给家人挑生日礼物。

这些任务之间可能没有强关联。默认新会话可以让用户直接开始当前任务，不需要先清理上一段对话背景。

### 2. 更适合导购链路的业务闭环

一次完整导购链路通常包括：

1. 理解需求
2. 补充条件
3. 搜索商品和知识
4. 推荐商品
5. 对比商品
6. 查看评价、优惠、库存
7. 加入购物车
8. 结算或继续浏览

这些动作天然属于一个任务闭环。用一个会话承载一个任务，结构更清楚，后续也更容易做会话摘要、历史检索、任务恢复和数据分析。

### 3. 更容易保证交易安全

电商系统和普通问答系统最大的区别之一，是导购结果会连接真实业务动作。

普通问答中，上下文错误通常只是回答不准；电商导购中，上下文错误可能导致：

- 推荐错商品
- 加购错商品
- 错用优惠券
- 结算错误商品
- 混淆订单状态

因此，产品形态必须优先保证当前任务的上下文清晰。默认新会话比默认继承上一段对话更安全。

### 4. 更利于用户管理历史购物决策

用户可能会在不同时间回看不同购物任务：

- “上次给我推荐的敏感肌洗面奶是哪几个？”
- “之前那组通勤耳机对比结果在哪里？”
- “露营装备清单能不能继续补充？”

如果按任务拆成多个会话，历史列表、搜索、置顶、删除、摘要都会更有价值。用户可以主动选择继续哪一个任务，而不是让系统自动猜测。

### 5. 更利于后续扩展个性化能力

默认新会话不代表完全放弃长期个性化。更合理的做法是区分两类信息：

- **任务上下文**：预算、品类、对比商品、临时使用场景，只在当前会话内继承。
- **长期偏好**：尺码、肤质、过敏源、常用品牌、价格带等，在用户明确授权或系统确认后沉淀为用户画像。

也就是说，长期偏好应该是被提炼后的稳定信息，而不是把所有历史对话原样继承给每一次新任务。

## 五、最终产品规则

基于以上分析，AI 导购采用以下规则：

1. **默认新会话**  
   用户进入 AI 导购首页或发起新的购物咨询时，默认创建新的会话，避免旧任务影响新任务。

2. **历史会话可继续**  
   用户可以从历史会话列表中搜索、置顶、删除和继续某个购物任务。

3. **同一会话内保留短期上下文**  
   在同一个购物任务中，支持“刚才那个”“第二个”“继续推荐”“加入购物车”等省略表达。

4. **跨会话不自动混入任务上下文**  
   不把上一段会话里的商品、预算、临时偏好默认带到新会话中。

5. **交易动作必须基于明确对象**  
   加购、结算、支付、取消订单等动作必须能定位到明确商品、购物车或订单对象；对象不明确时必须追问。

6. **长期偏好需要独立沉淀**  
   如果后续建设用户画像，应只沉淀稳定偏好，并在必要时让用户确认，而不是简单继承全部历史对话。

## 六、典型场景示例

### 场景 1：新购物任务默认隔离

用户昨天咨询：“帮我推荐敏感肌洗面奶。”

今天重新打开 AI 导购，输入：“推荐一款通勤耳机。”

系统应当把今天的问题当成新的购物任务处理，不自动继承昨天的洗面奶预算、肤质、商品列表和推荐理由。

### 场景 2：同一会话内连续追问

用户在当前会话中问：“推荐三款适合油皮的洗面奶。”

AI 返回三款商品后，用户继续说：“第二个加入购物车。”

系统可以根据当前会话中的商品卡片和商品 ID，明确“第二个”是哪款商品，然后执行加购。如果商品对象不明确，则需要追问。

### 场景 3：手动继续历史任务

用户从历史会话中打开“通勤耳机推荐”这段会话，继续问：“上次第二个和第三个再帮我对比一下。”

因为用户主动进入了这段历史会话，系统可以在该会话范围内使用短期记忆、摘要和商品引用，继续完成原来的购物任务。

## 七、产品表达

对用户来说，这个产品形态可以被理解为：

**每一段 AI 导购会话就是一个购物任务。新任务从干净上下文开始，旧任务可以随时回去继续；在同一个任务里，AI 会记得刚刚聊过的商品和条件，但不会把无关历史强行带进来。**

这种设计同时兼顾了导购连续性、交易安全、历史可管理性和后续个性化扩展空间。
