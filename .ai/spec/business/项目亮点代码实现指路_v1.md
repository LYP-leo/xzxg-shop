# 项目亮点代码实现与指路 v1

更新时间：2026-06-10

本文面向技术答辩和代码评审。它不重复描述“我们做了哪些功能”，而是回答三个问题：

1. 这个亮点解决了什么真实问题。
2. 代码里具体是怎么实现的。
3. 评委或同学应该从哪些文件、哪些函数顺着看。

如果只能讲三个亮点，建议按下面三个层次展开：客户端交互设计、Agent 能力建设、生产质量保障。它们刚好对应用户能感知的体验、系统的智能核心，以及能否生产化迭代。

## 亮点一：客户端交互设计

### 解决的问题

普通 AI 导购很容易变成“一个聊天框”：用户发一句话，等很久，最后得到一大段文本。这个形态有几个问题：

- 等待时间不可感知，用户不知道系统是在理解需求、查商品，还是卡住了。
- 大模型输出只是文本，和商品详情、购物车、订单这些真实电商控件脱节。
- 商品卡如果全部堆在回答末尾，用户很难把“推荐理由”和“对应商品”关联起来。
- 移动端购物天然需要图片、语音、TTS、追问等轻交互，而不是只靠键盘输入。

所以客户端的核心设计不是“渲染一段回答”，而是把 Agent 的运行过程拆成可感知、可点击、可恢复的购物体验。

### 核心实现链路

客户端主要消费后端 SSE 事件：

```text
message_start
thinking_delta
status
text_delta
block_delta / content_delta
followups
message_end
error
```

后端在流式接口中把文本、结构化块、追问、思考步骤都拆成事件；Android 客户端按事件类型增量渲染。这样用户一边等模型回答，一边能看到“正在分析需求”“正在查询商品和资料”等阶段性反馈。

代码入口：

- 后端 SSE 输出：[backend/src/httpapi/server.go](../../../backend/src/httpapi/server.go)
  - `handleAgentSessionAction()`：识别 `/messages:stream` 请求，创建 user message 和 run。
  - `streamAgentRun()`：设置 `text/event-stream`，把 `SSEEvent` 写给前端。
  - `emit()`：收集 `text_delta`、`block_delta`、`thinking_delta`、`followups`，同时持久化 segments。
- Android 流式消费：[android-native/app/src/main/java/com/xzxg/shop/chat/ChatActivity.java](../../../android-native/app/src/main/java/com/xzxg/shop/chat/ChatActivity.java)
  - `handleStreamEvent()`：按事件类型分发处理。
  - `appendAssistant()` / `appendAssistantText()`：处理增量文本、`<form>`、Markdown 表格和 `<item>` 标签。
  - `renderItemRefs()`：识别 `<item>product_id</item>` 后在当前位置附近插入商品卡。
  - `finishStream()`：收束当前轮回答，保存文本、blocks、followups、segments，并触发 TTS 收尾。
- Android Markdown 渲染：[android-native/app/src/main/java/com/xzxg/shop/ui/MarkdownRenderer.java](../../../android-native/app/src/main/java/com/xzxg/shop/ui/MarkdownRenderer.java)
  - 将模型输出的 Markdown 转成 Android 原生 TextView 可展示的富文本。
- Android 本地会话：[android-native/app/src/main/java/com/xzxg/shop/storage/LocalChatStore.java](../../../android-native/app/src/main/java/com/xzxg/shop/storage/LocalChatStore.java)
  - 保存本地消息、assistant segments、blocks、followups，支持历史会话恢复。
- Android TTS：[android-native/app/src/main/java/com/xzxg/shop/tts/TtsController.java](../../../android-native/app/src/main/java/com/xzxg/shop/tts/TtsController.java)
  - `startAssistantStream()`、`appendAssistantMarkdownDelta()`、`finishAssistantStream()`：把流式文本切成适合朗读的小段，避免等全文结束才播放。

### 商品卡片为什么能插在回答中间

这点是客户端交互的关键。我们没有让前端猜“这段话讲的是哪个商品”，而是让 Agent 输出协议中显式使用：

```xml
<item>p_xxx</item>
```

后端会校验 `p_xxx` 是否来自当前轮工具返回的商品白名单。客户端在流式文本里识别 `<item>`，把标签从用户可见文本中去掉，再在当前位置渲染商品卡。

相关代码：

- 协议文档：[.ai/api/Agent输出协议_v1.md](../../api/Agent输出协议_v1.md)
- 后端最终输出与挂品校验：[backend/src/agent/react.go](../../../backend/src/agent/react.go)
- Android 标签解析和卡片插入：[android-native/app/src/main/java/com/xzxg/shop/chat/ChatActivity.java](../../../android-native/app/src/main/java/com/xzxg/shop/chat/ChatActivity.java)

这个设计的好处是：模型负责“在哪里挂商品”，后端负责“这个商品能不能挂”，客户端负责“怎么渲染成卡片”。三层职责清晰，既保留了自然语言表达自由，也避免前端误判。

### 多模态与移动端体验

图片找同款和语音能力不应该只是一个孤立接口，而是要进入移动端导购体验：

- 图片上传后，后端可以用 `search_image_products` 工具走图片向量检索。
- 语音输入由客户端转成文字后进入同一套 Agent 链路。
- TTS 播放读取最终回答的流式文本，降低等待感。

代码入口：

  - `toolSearchImageProducts()`：从附件、file_id、object_key 或 image_url 获取图片，生成图片向量，并检索相似商品。
- 图片向量存储：[backend/src/store/mysql.go](../../../backend/src/store/mysql.go)
  - `SearchProductsByImageVector()`：到商品图片向量集合中召回相似商品。
- TTS 后端接口：[backend/src/httpapi/speech.go](../../../backend/src/httpapi/speech.go)
  - 负责 TTS 配置和语音合成接口。
- TTS 客户端播放：[android-native/app/src/main/java/com/xzxg/shop/tts/TtsPlaybackController.java](../../../android-native/app/src/main/java/com/xzxg/shop/tts/TtsPlaybackController.java)
  - 将后端返回的音频写入缓存并播放。

## 亮点二：Agent 能力建设

### 解决的问题

如果只是把用户问题直接丢给大模型，系统很难稳定：

- 模型可能编造商品、价格、库存和卖点。
- 模型可能口头说“已加购”，但实际上没有写购物车。
- 所有工具都暴露给模型，会导致调用无关工具，增加耗时和失败率。
- 复杂导购、购物车、订单、售后、优惠、图片找同款，本质上不是同一种任务。

所以后端把 Agent 设计成“意图路由 + 动态 Prompt + ReAct 工具循环 + 业务工具”的工程系统。

### 主链路从哪里看

最核心入口是：

- [backend/src/agent/runtime.go](../../../backend/src/agent/runtime.go)
  - Agent 单轮运行总入口：风控、记忆、意图、导购/非导购分支、最终收束。
- [backend/src/agent/react.go](../../../backend/src/agent/react.go)
  - `runReactAgent()`：导购和非导购主 Agent 的 ReAct 执行器。

`runReactAgent()` 是理解项目 Agent 能力的最重要函数。它做了几件事：

1. 根据前置 planner 得到的 `route / intent / model` 组装系统 Prompt。
2. 进入最多 6 步的 ReAct 循环。
3. 模型每轮只能输出两类协议：
   - `tool_call` / `skill_call` JSON。
   - `<final>...</final>` 最终回答。
4. 工具执行结果以 Observation 形式回填给模型。
5. 如果进入 `<final>`，后端直接把 final 内容流式转发给前端，不再额外调用一次“总结模型”。

这就是后来我们去掉 `react.final` 二阶段调用的原因：减少一次大模型耗时，同时用 `<final>` 自定义协议保留最后答案真流式。

### 动态 Prompt 与工具策略

不是每个意图都应该看到所有工具。比如场景方案需要 `search_products`、`search_knowledge`，但不一定需要 `update_cart_item`；购物车操作需要 `get_cart`、`add_cart_item`、`checkout`，但不应该暴露完整导购知识工具。

实现入口：

- [backend/src/agent/tool_policy.go](../../../backend/src/agent/tool_policy.go)
  - `intentToolPolicyPrompt()`：按当前子意图生成“可用工具、可用 skill、禁用能力、工具侧重”。
  - `toolAllowedForPlan()`：执行前做硬校验，不在策略里的工具不会被执行。
  - `finalOutputRulesPrompt()`：按当前工具集合追加最终输出硬约束。
- [backend/src/agent/prompts.go](../../../backend/src/agent/prompts.go)
  - 组装主 Agent、子意图、最终输出等 Prompt。
- [backend/src/configcenter/defaults.go](../../../backend/src/configcenter/defaults.go)
  - 代码默认 Prompt 和默认配置兜底。
- [backend/src/store/mysql.go](../../../backend/src/store/mysql.go)
  - `GetActiveAgentPrompt()`、`SaveAgentPromptDraft()`、`PublishAgentPrompt()`：Prompt 落库、草稿、发布。
- 管理员页面：[frontend/src/pages/admin/AdminPromptsPage.tsx](../../../frontend/src/pages/admin/AdminPromptsPage.tsx)
  - 后台编辑和发布 Prompt。

这个设计的重点是：Prompt 不是写死的一整段，而是在运行时由“基础规则 + 当前意图 + 可用工具 + 输出协议”拼出来。这样能减少无关工具暴露，也方便后台直接调 Prompt。

### 工具层如何闭环电商业务

Agent 工具集中定义在：

- [backend/src/agent/tools.go](../../../backend/src/agent/tools.go)

工具包括：

- 商品与知识：
  - `search_products`
  - `search_image_products`
  - `search_knowledge`
- 购物车：
  - `get_cart`
  - `add_cart_item`

- 订单：

  - `get_order`

  - `claim_coupon`

这些工具不是模拟数据，而是调用 Store 层落到真实业务表。Store 接口在：

例如加购不是模型说一句“已加入购物车”，而是执行 `toolAddCartItem()`，最终写入购物车表；结算不是跳页面，而是执行 `toolCheckout()`，创建订单、订单项、支付记录等业务数据。

### 真实商品召回与幻觉控制

这是 Agent 能力建设里最能体现工程价值的部分。核心链路是：

```text
用户 query
  -> planner 判断导购意图
  -> ReAct 决定调用 search_products / search_image_products
  -> Store 层做 MySQL + 向量召回
  -> 风控过滤风险商品/商家
  -> rerank 排序
  -> toolObservation 返回 product_ids / candidate_product_ids / dropped_product_ids
  -> runReactAgent 只把 relevance_status=ok 的商品加入允许挂品白名单
  -> final 输出中的 <item> 必须命中白名单
  -> 客户端按 product_id 渲染真实商品卡
```

相关代码：

- 商品工具入口：[backend/src/agent/tools.go](../../../backend/src/agent/tools.go)
  - `toolSearchProducts()`：商品工具总入口。
  - `EvaluateProductSearch()`：质量测评复用同一套工具逻辑，避免测评和线上不一致。
- 商品召回 Store：[backend/src/store/mysql.go](../../../backend/src/store/mysql.go)
  - `SearchProducts()`、`SearchProductsLimit()`：关键词与向量召回入口。
  - `SearchProductsByImageVector()`：图片向量召回入口。
- RAG/向量模块：
  - [backend/src/rag](../../../backend/src/rag)
  - [backend/src/vector](../../../backend/src/vector)
  - [backend/src/imagevector](../../../backend/src/imagevector)
- 最终挂品白名单：[backend/src/agent/react.go](../../../backend/src/agent/react.go)
  - `result.ProductIDs` 只收集相关性通过的工具返回商品。
  - 最终 `<item>` 只能引用这些商品。

这套链路解决了大模型导购最典型的问题：回答看起来很合理，但商品不存在，或者商品存在但和用户需求弱相关。项目里把“模型说什么”和“系统能挂什么商品”拆开，最终以工具返回的真实商品作为边界。

### 非导购能力为什么也放进 Agent

电商用户不只会问“买什么”，还会问：

- 我的订单在哪。
- 帮我结算。
- 优惠券怎么领。
- 这个商品评价怎么样。
- 帮我确认收货。

这些都不是传统导购问题，但如果不接入 Agent，用户体验会断掉。项目通过非导购链路和工具/skill 机制处理这些服务类需求。

相关代码：

- [backend/src/agent/non_guide_actions.go](../../../backend/src/agent/non_guide_actions.go)
  - 对加购、结算等确定性动作做直接工具执行，避免模型只输出固定话术。
- [backend/src/agent/skills.go](../../../backend/src/agent/skills.go)
  - 页面导航、固定服务能力等 skill。
- [backend/src/agent/tool_policy.go](../../../backend/src/agent/tool_policy.go)
  - 按非导购子意图限制可用工具和 skill。

## 亮点三：生产质量保障

### 解决的问题

大模型项目最难的不只是“能跑”，而是：

- 出问题时能不能定位是意图错、Prompt 错、工具错、召回错，还是模型输出错。
- 每次改 Prompt、改检索参数、换模型之后，效果有没有变好。
- 有没有风控、权限、幂等、限流、事务这些生产系统需要的基础能力。
- 管理员能不能在线调整 Prompt、配置、风险商品和测评数据。

所以项目做了链路追踪、质量测评、动态配置/Prompt 管理、风控和生产化中间件。

### 请求全链路 Trace

后端每次 Agent 请求都会创建 run 和 trace_id。关键数据会落到 `agent_runs` 和 `agent_trace_events`。

代码入口：

- 创建 message / run：[backend/src/httpapi/server.go](../../../backend/src/httpapi/server.go)
  - `handleAgentSessionAction()`：处理 `messages:stream`，创建用户消息和 Agent run。
  - `CreateUserMessage()` 与 `CreateRun()` 保证幂等，同一个 `client_message_id` 不会重复跑多次。
- SSE 与结果落库：[backend/src/httpapi/server.go](../../../backend/src/httpapi/server.go)
  - `streamAgentRun()`：把文本、blocks、followups、thinking segments 持久化。
  - 会话摘要异步执行，不阻塞用户主请求。
- trace 写入：[backend/src/agent/trace_schema.go](../../../backend/src/agent/trace_schema.go)
  - 统一 trace metadata 的 schema，拆分 input、output、debug。
- trace 存储：[backend/src/store/mysql.go](../../../backend/src/store/mysql.go)
  - `AppendTrace()`、`ListAgentTrace()`、`ListAgentTraceByRun()`。
- 管理员 trace 页面：[frontend/src/pages/admin/AdminDebugPage.tsx](../../../frontend/src/pages/admin/AdminDebugPage.tsx)
  - 请求列表、按用户 query 筛选、执行时间线、模型 Prompt、模型原始输出、工具结果、RAG 片段、向量库状态。

管理员页面可以看到：

- 当前 run 的用户 query。
- planner 和 ReAct 每一步。
- 每次 LLM 调用的实际 Prompt 和原始输出。
- 每个工具的 arguments、observation、候选商品、剔除商品、相关性原因。
- search_knowledge 返回的资料片段正文。
- 每一步耗时。

这让 bad case 排查从“猜模型为什么这么答”变成“按时间线复盘系统每一步看到了什么”。

### 质量测评体系

质量测评不是另写一套模拟逻辑，而是尽量复用线上接口和线上工具：

- 意图识别测评：看 route 和 intent 是否正确。
- RAG/商品召回测评：看预期商品或知识片段是否命中。
- Agent 端到端测评：看最终回答、结构化 blocks、工具调用是否符合预期。
- 图片检索和记忆检索也可以作为专项测评扩展。

代码入口：

- 测评脚本：[quality/evals](../../../quality/evals)
- 测评数据：[quality/data/eval](../../../quality/data/eval)
- 测评报告：[quality/reports](../../../quality/reports)
- 商品搜索测评复用线上工具：[backend/src/agent/tools.go](../../../backend/src/agent/tools.go)
  - `EvaluateProductSearch()` 直接调用 `toolSearchProducts()`。
- 管理员测评页面：[frontend/src/pages/admin/AdminEvalPage.tsx](../../../frontend/src/pages/admin/AdminEvalPage.tsx)
  - 展示测评套件、数据集、报告列表、报告详情、筛选和分页。

这个体系的价值是可回归。比如我们改了 rerank、改了否定语义、改了 Prompt，不应该只试一两个问题，而是跑同一批数据对比命中率、通过率、平均耗时、p95 耗时和失败 case。

### 动态 Prompt 与配置治理

Prompt 和模型配置不能散落在代码里，否则每次调 Prompt 都要重新发版。当前策略是：

- Prompt 主来源：数据库。
- 管理入口：管理员 Prompt 页面。
- Nacos：应用动态配置，例如模型供应商、key、检索权重、风控规则等。
- 代码默认值：兜底，保证本地开发环境能启动。

代码入口：

- Prompt Store：[backend/src/store/mysql.go](../../../backend/src/store/mysql.go)
  - `SeedAgentPrompts()`
  - `GetActiveAgentPrompt()`
  - `SaveAgentPromptDraft()`
  - `PublishAgentPrompt()`
- Prompt 管理接口：[backend/src/httpapi/server.go](../../../backend/src/httpapi/server.go)
  - `/api/v1/admin/prompts`
- Prompt 管理前端：[frontend/src/pages/admin/AdminPromptsPage.tsx](../../../frontend/src/pages/admin/AdminPromptsPage.tsx)
- 动态配置中心：[backend/src/configcenter](../../../backend/src/configcenter)
- 模型角色选择：[backend/src/agent/model_roles.go](../../../backend/src/agent/model_roles.go)

这样评审时可以强调：我们不是把 prompt 写死，而是让 Prompt 有版本、草稿、发布和后台可视化管理。

### 生产化中间件

项目不是单进程内存 demo，而是接入了真实中间件：

- MySQL：用户、商品、购物车、订单、会话、trace、Prompt。
- Nacos：动态配置。
- Milvus：商品、知识、图片向量。
- MinIO：文件和图片对象存储。
- Redis：预留给缓存、限流和任务状态。

## 建议答辩讲法

如果时间只有 3 分钟，可以这样说：

1. 客户端层面，我们把 Agent 的输出从纯文本升级成移动端购物体验：流式回答、思考过程、Markdown、商品卡插入、追问、图片和语音都在同一套协议里渲染。
2. Agent 层面，我们没有直接拿大模型生成商品推荐，而是用意图路由、动态 Prompt、ReAct 工具循环和真实电商工具，让模型在真实商品库、购物车、订单、评价、图片检索上工作。
3. 生产保障层面，我们做了 trace、测评、Prompt 管理、风控、幂等、事务和中间件接入，确保 bad case 能定位、改动能回归、线上行为可控。

如果评委要看代码，推荐按这个顺序打开：
