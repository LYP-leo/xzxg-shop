# 小猪小狗电商导购项目亮点与方案梳理 v1

更新时间：2026-06-06

## 1. 总体定位：不是聊天机器人，而是电商 AI 导购系统

小猪小狗项目的核心不是“在电商页面里接一个大模型聊天框”，而是把大模型接入真实电商业务系统，让它能在商品库、购物车、订单、优惠、评价、知识库、风控、质量测评和管理后台这些真实业务能力之上工作。

如果只做聊天机器人，模型只需要回答得像人。但电商导购系统不一样，它必须做到：

- 推荐的商品必须真实存在。
- 价格、库存、优惠、售后规则不能编造。
- 用户说“不要苹果”时，系统不能继续推荐苹果。
- 用户要求加购、结算、查订单时，要真的调用业务系统，而不是只说“已为你处理”。
- 出现 bad case 时，管理员要能看到模型为什么这么答、工具查到了什么、哪些商品被剔除了。
- 每次优化 Prompt、模型、检索策略之后，要能用测评数据回归。

因此，这个项目的价值链路可以概括为：

```text
用户表达需求
  -> 系统判断意图
  -> Agent 动态组织 Prompt、工具和 skill
  -> 查真实商品和知识，控制幻觉
  -> 支持图片和语音等多模态输入
  -> 用流式协议把思考过程、文本和商品卡展示给用户
  -> 管理员能追踪每一步
  -> 测评体系沉淀 bad case 并回归
  -> 生产化基础保障系统可落地
```

下面的亮点也按这条链路展开。这样讲的时候，不是零散罗列技术点，而是能从一次用户请求进入系统开始，把每个模块为什么存在、解决什么问题、为什么选择当前方案串起来。

## 2. 亮点一：意图分类，让请求先走对业务链路

### 2.1 面对的问题

电商聊天入口里，用户输入不只有“推荐商品”。同一个入口可能出现：

- “帮我推荐一台写代码的电脑”。
- “华为电脑和苹果电脑怎么选？”
- “刚才那款加入购物车”。
- “我有哪些优惠券？”
- “最近订单到哪了？”
- “这个商品差评主要说什么？”
- “你好。”

这些请求背后的业务链路完全不同。如果不先判断意图，主 Agent 就会面临两个问题：

1. 所有工具都暴露给模型，Prompt 过长，误调用概率高。
2. 用户要求真实业务动作时，模型可能只输出文案；用户只是咨询时，模型又可能误执行写操作。

电商系统里，尤其是购物车、订单、结算这类动作，误执行比不执行更严重。因此意图分类不是锦上添花，而是安全边界和业务路由的入口。

### 2.2 历史方案和问题

早期可以用关键词硬编码，例如看到“加购”“购物车”就直接进入购物车链路。这种方案简单，但在真实对话里问题很明显：

- Prompt、工具说明、历史记忆里也可能出现“加购”，容易误触发。
- 用户表达不一定包含固定关键词，例如“就买这个吧”“这个放进去”“刚才那款我要了”。
- 一句话里可能既有导购又有交易动作，需要判断主意图。
- 规则越写越多，后续维护困难。

另一个极端是完全让主 Agent 自己判断所有事情。但这样会导致主 Prompt 过长，所有工具都要放进去，模型容易混淆当前到底能调用哪些能力。

### 2.3 当前方案

当前采用两层意图体系。

第一层判断 route：

- `guide`：导购链路，解决推荐、对比、选购、单品咨询、场景方案。
- `non_guide`：非导购服务链路，解决购物车、订单、优惠、评价、售后、账号、导航、闲聊等服务。

第二层继续细分具体 intent。

导购意图包括：

- `product_deep`：用户已锚定具体商品，做单品深度咨询。
- `compare_decide`：多个商品、品牌、品类或参数路线之间对比决策。
- `outfit_styling`：穿搭、组合、搭配建议。
- `category_shop_brand`：有品牌的品类选购。
- `category_shop_no_brand`：无品牌的品类选购。
- `category_shop_complex`：多条件复杂筛选。
- `scene_solution`：场景方案和清单。
- `open_explore`：开放探索式选购。

非导购意图包括：

- `cart_service`
- `order_service`
- `coupon_service`
- `review_service`
- `after_sales_service`
- `account_service`
- `navigation_service`
- `chitchat`
- `unsupported`

代码还支持更具体的动作 intent：

- `cart_add`
- `cart_remove`
- `cart_update_quantity`
- `checkout_confirm`

### 2.4 为什么选择小模型做 planner

planner 的任务是分类和路由，不是生成长回答。它更适合用小模型：

- 成本更低。
- 响应更快。
- 输出结构化 JSON。
- 让大模型专注后续复杂推理和最终表达。

这也是当前“轻 planner + 主 Agent ReAct”的分工：小模型判断“用户要什么”，主 Agent 决定“怎么完成”。

### 2.5 这个亮点怎么讲

可以这样讲：

> 我们没有把所有请求都丢给一个大 Prompt，而是先做两层意图分类。第一层判断导购还是非导购，第二层判断具体业务域。分类结果会影响工具白名单、Prompt 范式、是否允许写操作和最终输出协议。这样既降低成本，也减少误调用，让 Agent 更像一个带路由和权限控制的业务系统。

## 3. 亮点二：主 Agent 编排与动态 Prompt 拼接

### 3.1 面对的问题

电商 Agent 不是单轮问答。它可能需要：

- 理解用户真实需求。
- 判断要不要查商品。
- 判断要不要查知识库。
- 判断要不要查购物车或订单。
- 对工具返回结果做下一步决策。
- 最后把结果组织成用户能看懂的导购回答。

如果把所有规则、所有工具、所有意图范式都写进一个固定 Prompt，问题会很明显：

- Prompt 太长，模型容易忽略关键规则。
- 每个请求都携带大量无关工具，误调用概率高。
- 不同意图的输出风格难区分。
- Prompt 修改后难判断影响了哪些链路。

### 3.2 历史方案和问题

早期方案偏固定流程：用户输入后先检索商品，再按模板回答。这能快速做出演示，但无法处理复杂场景：

- 用户问的是售后规则，不一定要推荐商品。
- 用户要求加购，需要真实写购物车。
- 用户要求对比，需要分别检索候选商品和知识。
- 用户发图片，需要调用图片搜索。

后来升级为 ReAct，但最初 Prompt 拼得比较粗，把工具协议、全局规则、子意图规则和硬约束重复写在一起。实际运行时 Prompt 过长，不利于模型稳定遵守，也不利于后台运营。

### 3.3 当前主链路

当前主链路是：

```text
用户输入
  -> 风控检查
  -> 短期记忆检索
  -> 小模型 planner 判断 route / intent
  -> 根据 intent 动态拼接主 Agent Prompt
  -> ReAct 循环决定 tool_call / skill_call / <final>
  -> 执行工具并把 observation 回填给模型
  -> 信息足够后进入 <final> 真流式输出
  -> 输出文本、商品卡、表格、追问和思考过程
  -> trace 和质量数据落库
```

### 3.4 动态 Prompt 拼接做了什么

当前 Prompt 不是一整块写死，而是按请求动态组装：

1. Agent 身份和核心原则：
   - 不能编造商品和业务事实。
   - 商品、知识、购物车、订单等信息必须通过工具获取。
   - 信息不足时说明资料不足或澄清。

2. 工具调用阶段协议：
   - `tool_call` JSON。
   - `skill_call` JSON。
   - 当前可用工具。
   - 当前可用 skill。
   - 禁用能力。
   - 当前意图下的工具使用侧重。

3. 子意图内容范式：
   - `product_deep` 强调围绕单品回答。
   - `compare_decide` 强调横向对比和表格。
   - `scene_solution` 强调清单框架和场景风险。
   - 非导购服务强调业务数据和结构化 block。

4. 最终输出协议：
   - 必须用 `<final>...</final>`。
   - `<item>` 只能写真实 `product_id`。
   - `<item>` 要靠近对应商品说明。
   - 表格必须放在 `<form>...</form>`。
   - 禁止把内部字段、工具名、`relevance_status` 等调试信息写给用户。

### 3.5 Tool 和 skill 的分工

项目里把能力分成 tool 和 skill：

- tool：真实查数据或改数据，例如搜索商品、搜索知识、读取购物车、加购、结算、查订单、查优惠、图片搜索。
- skill：固定业务入口或页面动作，例如打开购物车、打开订单页、查看优惠入口。

这样做的好处是：模型不用直接知道前端页面细节，也不用把“打开购物车”伪装成自然语言。它可以调用 skill，后端返回结构化 action block，前端再渲染对应入口。

### 3.6 为什么用 ReAct

ReAct 适合这里，是因为一次电商导购请求通常需要多步决策：

```text
先查商品
  -> 如果结果不足，再查知识
  -> 如果发现用户有排除条件，重新检索或过滤
  -> 如果信息足够，输出最终回答
```

模型每一步只需要决定下一步是调用工具、调用 skill，还是输出最终回答。工具策略又限制了它不能调用当前意图不允许的能力。

### 3.7 为什么用 `<final>` 自定义协议

项目早期考虑过两阶段方案：ReAct 工具循环结束后，再额外调用一次 LLM 生成最终回答。这个方案稳定，但响应时间更长。

当前改为单阶段真流式：

- 模型在 ReAct 循环里先输出 JSON 工具调用。
- 信息足够时直接输出 `<final>...</final>`。
- 后端识别到 `<final>` 后，立即把标签内正文流式转发给前端。
- 不再额外调用一次 `react.final`。

这样减少一次大模型调用，降低 RT，同时保留最终回答的流式体验。

### 3.8 这个亮点怎么讲

可以这样讲：

> 我们的主 Agent 不是一个静态 Prompt，而是一个动态编排系统。前置小模型先判断意图，后端再根据意图拼接可用工具、可用 skill、禁用能力和对应内容范式。主 Agent 在 ReAct 循环中按协议调用工具，信息足够时直接进入 `<final>` 真流式输出。这样既保证了复杂任务的灵活性，又把工具权限和输出格式控制在后端。

## 4. 亮点三：真实商品召回与大模型幻觉控制

### 4.1 面对的问题

电商场景里，大模型幻觉比普通问答更危险。它可能编造：

- 商品不存在。
- 价格、库存、优惠不真实。
- 售后承诺没有依据。
- 用户要求“不要苹果”，却仍推荐苹果。
- 商品库没有马桶，却拿数码商品硬凑推荐。
- 用户问“华为电脑”，召回了手机或无关商品。

这类错误会直接影响交易信任。如果用户根据 AI 推荐购买，后续发现商品不存在或承诺不成立，平台要承担售后和信任成本。

### 4.2 对比方案和问题

方案一：把商品信息拼进 Prompt，让模型自己答。

问题：

- 商品多了放不下。
- 模型会把通用知识和商品库混在一起。
- 商品 ID、价格、库存没有强校验。
- 无法判断最终挂出的商品是否真实来自本轮召回。

方案二：只用 MySQL 关键词搜索。

问题：

- “苹果本”“MacBook”“写代码电脑”这类语义表达不一定命中标题。
- “不要苹果”这类否定条件很难靠简单 LIKE 处理。
- 场景词、痛点词、功效词和商品属性之间缺少语义桥梁。

方案三：只用向量搜索。

问题：

- 向量能解决语义相似，但可能召回“看起来相关、业务上不该推荐”的商品。
- 例如用户问“苹果电脑”，可能召回苹果手机；用户问“马桶”，可能因为“家用、智能、白色”等特征召回无关家电。

### 4.3 当前方案，用业务链路解释

当前方案可以先不用技术名词理解。我们做的是：不让大模型直接凭感觉推荐商品，而是让它像一个导购员一样，先去平台商品库查货，再根据查到的真实商品回答，最后只有查到的商品才允许展示成商品卡。

用户一次提问进来后，链路大致是这样：

```text
用户说：“推荐一台写代码和做演示用的电脑，不要苹果”
  -> Agent 先理解：用户要买电脑，场景是写代码和演示，排除苹果
  -> Agent 不能直接回答，必须先调用商品搜索能力
  -> 搜索系统去真实商品库里查“电脑”，同时把“苹果”作为排除条件
  -> 搜索系统返回候选商品，并标记哪些商品相关、哪些商品被剔除、为什么剔除
  -> Agent 只能基于这些真实候选组织回答
  -> 如果要在回答里插入商品卡，只能插入本轮搜索返回过的商品 ID
  -> 如果商品库没有合适商品，必须告诉用户“当前商品库暂时没有找到”，不能拿无关商品凑数
```

也就是说，我们把“推荐商品”拆成了三个关口：

1. 回答前必须查库：模型不能跳过商品库直接编答案。
2. 查库结果必须相关：不是搜到任何商品都能推荐，要经过相关性判断。
3. 最终挂品必须校验：前端展示的商品卡必须来自本轮真实召回，不能由模型编造。

### 4.4 具体召回链路

真实商品召回不是一个单点搜索接口，而是一条从“用户自然语言”到“前端商品卡”的完整链路。

```text
用户 query
  -> planner 判断导购意图
  -> 主 Agent 生成 search_products 工具调用
  -> 后端解析工具参数
  -> 构建商品检索计划
  -> MySQL 结构化召回
  -> Milvus 向量召回
  -> 候选合并去重
  -> 业务过滤与风控过滤
  -> 相关性重排
  -> 弱相关判断和剔除
  -> 返回可推荐商品 + 被剔除商品 + 原因
  -> 主 Agent 基于工具结果生成 <final>
  -> 后端校验 <item> 商品 ID 白名单
  -> SSE 输出文本和商品卡
  -> 前端按 content_delta 渲染商品卡
```

下面按阶段展开。

#### 4.4.1 用户 query 到工具调用

用户输入通常是自然语言，不是结构化搜索条件。例如：

```text
推荐一台写代码和做演示用的电脑，不要苹果
```

planner 先判断这是导购请求，并细分到对应导购意图，例如 `category_shop_complex` 或 `compare_decide`。随后主 Agent 会根据当前意图 Prompt 和工具策略决定调用 `search_products`。

理想的工具调用不是把整句话原封不动丢给搜索，而是把搜索目标压缩成稳定的商品检索 query，并把排除条件单独表达：

```json
{
  "type": "tool_call",
  "tool": "search_products",
  "arguments": {
    "query": "电脑",
    "limit": 5,
    "negative": {
      "brands": ["苹果"],
      "terms": ["MacBook", "苹果电脑"]
    }
  }
}
```

这里的关键是：场景信息“写代码、做演示”不一定适合直接塞进首次搜索 query，它更适合在后续重排和回答解释时使用。否则 query 太长，可能导致检索发散或命中不稳定。

#### 4.4.2 构建商品检索计划

后端收到 `search_products` 后，会把模型给出的参数转换成检索计划。这个计划会区分：

- 正向检索词：用户真正想找什么，例如“电脑”“华为电脑”“面霜”。
- 否定条件：用户明确不要什么，例如“不要苹果”“不要酒精”。
- 数量限制：本轮最多返回多少候选。
- 上下文约束：当前用户、当前会话、附件图片、历史 observation 中的商品 ID。
- 业务过滤条件：商品状态、商家状态、风控状态、库存等。

这样做的意义是：模型负责表达需求，后端负责把需求变成可执行、可审计、可过滤的检索计划。

#### 4.4.3 MySQL 结构化召回

MySQL 召回负责保证“商品真实存在”和“业务字段可信”。它查的是平台真实商品表和相关结构化数据：

- 商品 ID。
- 商品名。
- 品牌。
- 类目。
- 价格。
- 库存。
- 商家。
- 商品状态。
- SKU。
- 销售属性。

MySQL 这一路适合处理：

- 明确品牌词，例如“华为”“苹果”“薇诺娜”。
- 明确品类词，例如“电脑”“面霜”“跑鞋”。
- 商品名关键词。
- 结构化过滤，例如状态、商家、风控、库存。

它的价值是强事实性：只要从 MySQL 返回，就代表商品是真实业务数据，不是模型编出来的。

#### 4.4.4 Milvus 向量召回

Milvus 负责补足关键词搜索的不足。用户经常不会说商品标题，而是说场景、痛点或近义表达，例如：

- “写代码电脑”
- “适合演示的轻薄本”
- “敏感肌修护”
- “脸干痒用什么”
- “通勤跑鞋”

这些词不一定直接出现在商品标题里，但可以通过商品描述、知识片段、商品 embedding 找到相关商品。

当前向量召回覆盖：

- 商品文本向量。
- 知识片段向量。
- 商品图片向量。

文本商品召回用于解决语义匹配，图片向量召回用于“拍照找同款/相似款”。

#### 4.4.5 候选合并、去重和业务过滤

MySQL 和 Milvus 可能返回同一个商品，也可能返回不同商品。后端会把候选合并去重，形成统一候选池。

随后会做业务过滤：

- 商品是否上架。
- 商家是否可用。
- 商品是否被风控。
- 商家是否被风控。
- 是否命中用户明确否定条件。
- 是否存在可售库存。

这一步很重要，因为召回系统可能“找到了”，但业务上不一定“能推荐”。例如商品被下架、商家被风控、商品命中风险标签，都不能继续进入可推荐列表。

#### 4.4.6 相关性重排

过滤后，系统会对候选做重排。重排不是只看一个分数，而是综合多个信号：

- 关键词匹配度。
- 向量相似度。
- 品牌/品类匹配度。
- 用户 query 中的核心词覆盖。
- 场景词匹配。
- 否定条件惩罚。
- 商品状态和业务可推荐性。

例如用户说“华为电脑”，商品标题中只有“华为手机”的候选即使品牌匹配，也因为品类不匹配而被打低或剔除。用户说“不要苹果”，苹果相关商品即使语义相关，也会被惩罚。

#### 4.4.7 弱相关判断

重排后还要判断“有没有可靠命中”。这是为了解决一个常见问题：搜索系统总能返回一些东西，但返回了东西不代表应该推荐。

例如：

```text
用户问：推荐马桶
商品库：没有马桶
召回候选：智能音箱、手机、电脑
```

如果只按 topK 返回，模型可能会拿这些无关商品硬写推荐。当前方案会把这类结果标记为弱相关或无可靠命中：

- `relevance_status=ok`：可以作为推荐依据。
- `relevance_status=weak`：弱相关，不能直接挂品推荐。
- `product_ids=[]`：没有可靠商品。
- `dropped_product_ids`：被剔除的候选。
- `relevance_reason`：剔除或弱相关原因。

这样主 Agent 看到工具结果后，不能继续推荐无关商品，而应该告诉用户当前商品库暂时没有合适商品，或者请用户换一个品类/条件。

#### 4.4.8 工具结果回填给主 Agent

`search_products` 返回的不只是商品 ID，还会包含模型成文需要的依据：

- 商品名。
- 商品 ID。
- 价格。
- 卖点。
- 风险提示。
- 库存状态。
- 图片。
- 相关知识或片段。
- 相关性状态。

主 Agent 只能基于这些 observation 组织回答。它可以解释为什么推荐某个商品，但不能编造工具结果里没有的价格、优惠、库存和售后承诺。

#### 4.4.9 最终 `<item>` 白名单校验

模型最终回答中可以写：

```text
这款更适合写代码和演示，性能和便携更均衡。
<item>p_laptop_001</item>
```

但后端不会盲信模型。后端会检查：

- `p_laptop_001` 是否来自本轮 `search_products` 返回。
- 该商品是否通过相关性判断。
- 该商品是否没有被风控或业务过滤。
- 该商品是否在本轮允许挂品白名单里。

只有通过校验，后端才会把它转换成前端可以渲染的商品卡事件。否则会过滤掉这个 `<item>`，避免模型编造或错挂商品。

#### 4.4.10 前端商品卡渲染

最终输出不是让前端从自然语言里猜商品，而是通过结构化事件渲染：

- 文本走 `text_delta` 或 `content_delta.text`。
- 商品卡走 `content_delta.product_card`。
- 旧客户端也可以继续消费 `block_delta.product_card`。

这样前端展示的商品卡来自后端结构化数据，而不是从模型文本里解析出来的商品名。

### 4.5 为什么选择当前方案

这个方案把模型和业务系统的职责分开：

- 模型负责理解需求、组织回答、做决策表达。
- 工具负责返回真实商品、真实订单、真实购物车、真实优惠。
- 后端负责校验边界，禁止模型越权编造商品和动作。

它比“完全相信模型”更安全，比“纯规则搜索”更灵活，也比“纯向量检索”更可控。

### 4.6 这个亮点怎么讲

可以这样讲：

> 我们不是让大模型直接推荐商品，而是把商品推荐变成一个受约束的工具调用流程。模型必须先查真实商品库，后端再基于工具结果做白名单过滤和弱相关拦截。最后能挂出的商品卡，必须来自本轮真实召回结果。这样既保留了大模型理解自然语言需求的能力，又避免了电商场景最危险的商品幻觉。

## 5. 亮点四：多模态图片与语音输入

### 5.1 面对的问题

移动端电商用户不一定会用文字描述商品。他们可能：

- 拍一张商品图，问“找同款”。
- 发截图，问“这个怎么样”。
- 用语音输入一段很口语化的需求。
- 图片里没有文字，OCR 完全无效。

如果系统只支持文本，就无法覆盖很多真实导购场景。

### 5.2 图片方案演进

最初可以只做 OCR：

- 优点是实现简单，适合包装、标签、商品名截图。
- 问题是对无文字图片无效，例如鞋子、包、衣服、鼠标。

当前方案升级为图片向量检索：

- 上传图片到 MinIO。
- 对商品图片和用户上传图片生成 embedding。
- 写入 Milvus 图片向量集合。
- 用户发图时由 Agent 决策是否调用 `search_image_products`。
- 根据相似图片召回商品，再由 Agent 结合用户文字判断是否推荐。

当前默认语义图片 embedding 使用 DashScope `qwen3-vl-embedding`，同时保留本地颜色直方图 fallback。

### 5.3 为什么图片搜索做成 tool

图片搜索没有硬写进主流程，而是做成 `search_image_products` tool。原因是：

- 不是所有带图请求都需要图片检索，模型要根据 query 和附件决定。
- 图片结果也需要进入统一 trace。
- 图片召回结果要和商品检索、知识检索一样受白名单约束。
- 后续更换 VLM、OCR、embedding 模型，不影响 Agent 协议。

这符合项目整体设计：业务能力通过 tool 暴露，Agent 负责决策调用。

### 5.4 语音交互的定位

语音主要是前端交互能力：

- 用户可以按住说话输入 query。
- 前端负责录音、状态展示、语音转文本或语音链路对接。
- 后端 Agent 最终仍处理标准化文本 query 和附件。

这样划分的好处是：

- Agent 主链路不被语音采集细节污染。
- Android 可以重点优化移动端体验。
- 后续语音识别服务替换，不影响 Agent 业务协议。

### 5.5 这个亮点怎么讲

可以这样讲：

> 我们没有把多模态做成独立 demo，而是把图片找同款接入同一套 Agent 工具体系。图片上传后进入对象存储，图片 embedding 写入 Milvus，用户带图请求时由 Agent 决策是否调用图片搜索 tool。图片召回出来的商品仍然走真实商品白名单和最终输出协议。语音则作为移动端输入体验，让用户能用更自然的方式表达需求。

## 6. 亮点五：流式推送与交互体验优化

### 6.1 面对的问题

AI 导购请求通常比普通接口慢，因为它可能包含：

- 意图分类。
- 记忆检索。
- 商品检索。
- 知识检索。
- 图片 embedding。
- 多次工具调用。
- 最终回答生成。

如果用户只能等待一个完整响应，会觉得系统卡住了。尤其在移动端，等待感会明显影响体验。

### 6.2 历史方案和问题

早期可以简单返回完整 JSON：

- 实现简单。
- 但用户看不到中间状态。
- 失败时不知道卡在哪。
- 商品卡只能在最后一起出现。

后来支持 `text_delta` 流式文本，但又出现新问题：

- 商品卡片集中在消息底部，和对应说明分离。
- 前端难以展示“正在分析、正在查商品、正在总结”的过程。
- 如果最终回答还要额外调一次 LLM，RT 会继续变长。

### 6.3 当前 SSE 协议

当前 Agent 与前端通过 SSE 通信，主要事件包括：

- `message_start`：本轮开始，返回 run_id、session_id、trace_id。
- `status`：当前阶段状态，例如理解需求、查询商品、生成回答。
- `thought_step`：思考过程节点，用于展示“分析用户需求、查询资料、总结答案”。
- `text_delta`：兼容旧前端的文本流。
- `content_delta`：按生成顺序输出文本片段、商品卡片等内容。
- `block_delta`：结构化卡片，例如商品、购物车、订单、引用、action。
- `followups`：推荐追问。
- `message_end`：本轮结束。
- `error`：错误事件。

### 6.4 交互优化做了什么

第一，最终回答真流式：

- 使用 `<final>...</final>` 协议。
- 模型一旦进入 `<final>`，后端立即把标签内文本流式发给前端。
- 不再额外执行第二次 `react.final` 大模型调用。

第二，商品卡顺序插入：

- Prompt 要求 `<item>` 靠近对应商品说明。
- 后端把 `<item>` 转成 `content_delta.product_card`。
- 前端可以做到“先讲商品 A -> 插入商品 A 卡 -> 再讲商品 B -> 插入商品 B 卡”。

第三，思考过程可视化：

- 主回答开始前显示“思考中”。
- 分析用户需求、查询商品资料、总结答案按步骤更新。
- 主回答开始输出时才变成“已完成思考”。
- 查询商品时可以展示商品小图轮播，让用户知道系统确实查到了候选。

第四，前端状态和后端 trace 打通：

- 用户看到的是交互状态。
- 管理员看到的是同一 run_id 下的详细 trace。
- 同一个请求既能提升体验，也能支撑排障。

### 6.5 这个亮点怎么讲

可以这样讲：

> 我们没有等模型整段回答完成后再返回，而是设计了 SSE 流式协议。文本、商品卡、思考步骤、追问、错误都通过事件分发。最终回答用 `<final>` 协议实现单次模型调用内真流式，商品卡通过 `content_delta` 按生成顺序插入正文中间。这样既降低用户等待感，也让 Android 客户端可以做出类似主流 AI App 的思考过程和即时反馈体验。

## 7. 亮点六：可观测和排障体系，让 AI 不再是黑盒

### 7.1 面对的问题

AI 系统一旦出错，只看最终回答是不够的。比如：

- 用户问“华为电脑”，为什么没有召回华为电脑？
- 商品库没有马桶，为什么推荐了数码商品？
- 用户只是说“干性皮肤”，为什么进入了加购链路？
- 模型为什么把内部字段 `relevance_status` 写给用户？
- 图片找同款为什么向量生成失败？

这些问题如果没有 trace，只能靠重复复现和猜测，很难定位。

### 7.2 当前方案

项目在管理员端建设了请求全链路追踪。每次 Agent 请求都有 run_id 和 trace_id，后台可以看到：

- 用户原始 query，作为请求标题。
- planner 的 route 和 intent。
- 每次 LLM call 的实际 prompt。
- 模型原始输出。
- 每次 tool call 的工具名、参数、结果和耗时。
- `search_products` 的候选商品、命中商品、剔除商品和弱相关原因。
- `search_knowledge` 的具体资料片段。
- 图片搜索和 embedding 的执行结果。
- 最终输出和 SSE 事件。

这让 bad case 能从“感觉不对”变成“定位到哪一步不对”。

### 7.3 和用户体验的关系

用户端看到的是“正在分析需求、正在查询商品、正在生成回答”。管理员端看到的是同一个 run_id 下的详细内部 trace。

这两个视角打通后，有两个好处：

- 用户等待时有反馈。
- 管理员排障时能对上用户看到的那次请求。

### 7.4 这个亮点怎么讲

可以这样讲：

> 我们把 Agent 的每一步都做成可观测事件。管理员不仅能看到最终回答，还能看到每次 LLM 的真实 prompt、模型原始输出、工具参数、召回片段、候选商品、剔除原因和耗时。这样 AI 系统不再是黑盒，bad case 可以被定位、复现和沉淀。

## 8. 亮点七：质量测评体系，从人工感觉走向回归闭环

### 8.1 面对的问题

AI 导购系统很容易陷入“人工试几条觉得还行”的误区。但真实质量问题包括：

- 意图是否分对。
- 工具是否调对。
- 检索 query 是否合理。
- RAG 是否召回正确商品和知识。
- 最终回答是否基于证据。
- 是否出现无关商品、内部字段、幻觉承诺。
- 图片处理是否明显拖慢 RT。

如果没有测评体系，每次改 Prompt、改模型、改 rerank 权重，都不知道整体质量是变好还是变坏。

### 8.2 历史问题

早期 RAG 测评数据使用了过长 keyword，例如把品牌、完整商品标题、FAQ 原文都放进查询。这会造成“看起来召回率很高”，但实际上是信息泄漏。

真实用户不会说完整商品标题，他们会说：

- “薇诺娜 面霜”
- “敏感肌修护”
- “华为电脑”
- “不要苹果的电脑”
- “写代码做演示用什么电脑”

因此测评数据必须从“精确回查”改成“真实用户短 query + 标注期望商品/片段”。

### 8.3 当前测评分层

当前质量体系分为几层：

1. 意图识别测评：
   - 输入用户 query。
   - 调用线上同一套 intent 分类接口。
   - 输出 predicted intent、expected intent、accuracy。

2. RAG 召回测评：
   - 输入真实短 query。
   - 测 Hit@K、Recall@K、首个相关结果位置。
   - 看是否召回期望商品或 chunk。

3. Agent 端到端测评：
   - 真实调用后端 Agent 流式接口。
   - 记录回答、blocks、run_id、trace_id。
   - 可人工检查或后续接 LLM judge。

4. 图片搜索测评：
   - 测图片向量生成、相似商品召回、处理耗时。
   - 评估图片链路对用户一次请求 RT 的影响。

5. 管理员可视化：
   - 测评报告可以在后台查看。
   - 支持筛选、分页、报告详情。
   - 和 trace 联动排查 bad case。

### 8.4 为什么测评接口要复用线上逻辑

一个关键取舍是：测评脚本不是复制一套离线逻辑，而是调用后端提供的测评接口。这样做是为了保证测评链路和线上链路一致。

例如意图测评接口必须调用线上 Agent 使用的同一个分类函数。如果测评脚本自己写一套规则，测出来再高也不能代表线上效果。

### 8.5 质量闭环

质量体系让项目具备迭代闭环：

```text
线上 bad case
  -> trace 定位问题
  -> 加入测评数据集
  -> 修改 Prompt / 工具策略 / 检索权重 / rerank
  -> 批量回归测评
  -> 管理员页面查看报告
```

### 8.6 这个亮点怎么讲

可以这样讲：

> 我们把 Agent 质量拆成意图识别、工具调用、RAG 召回、端到端回答和响应耗时几个层级，而不是只看最终回答。测评数据从长标题精确匹配改成真实用户短 query，并且测评接口复用线上逻辑，避免测试和线上漂移。每个 bad case 都可以沉淀成数据集，用来驱动 Prompt、检索和工具策略迭代。

## 9. 亮点八：生产化电商基础，让 Agent 接得住真实业务

### 9.1 面对的问题

很多 AI demo 只证明模型能回答，但真实电商系统还需要：

- 用户、商家、管理员三类角色。
- 商品、SKU、库存、购物车、订单、支付、优惠、评价等基础链路。
- 鉴权、权限、风控、限流、日志。
- 幂等、事务、库存预留。
- 文件和图片存储。
- 动态配置和 Prompt 管理。

如果没有这些能力，Agent 只能停留在演示层，不能真的接入业务。

### 9.2 当前已做的生产化能力

账号和权限：

- 登录注册。
- 用户、商家、管理员三端角色。
- bcrypt 密码哈希。
- 旧 hash 兼容迁移。
- bearer token 只存 SHA-256 摘要。

接口和安全：

- 接口分页。
- 请求日志。
- 限流。
- body size 限制。
- CORS 和可信代理配置。
- 风控词和风险账号、风险商品、风险商家拦截。

交易链路：

- 购物车 upsert。
- 加购、修改数量、删除、选中状态。
- 结算事务。
- 库存预留。
- 订单、订单项、支付记录。

文件和多模态基础：

- MinIO 存图片和文件。
- 文件下载鉴权。
- MIME 类型服务端检测。
- 图片 embedding 和 Milvus 图片向量。

动态配置和运营：

- Nacos 管理运行配置。
- Prompt 向数据库管理演进。
- 管理员页面维护配置、Prompt、风控、测评报告和 trace。

### 9.3 为什么这也是亮点

AI 导购要真正落地，不能只回答“推荐你买 X”。它还需要知道：

- X 是否真实存在。
- X 是否有库存。
- 能不能加入购物车。
- 当前用户有没有优惠券。
- 下单是否会扣库存。
- 如果商品或用户被风控，是否应该拦截。

这些都依赖电商基础链路。因此生产化基础能力是 Agent 可信落地的底座。

### 9.4 这个亮点怎么讲

可以这样讲：

> 我们不是单独做一个 AI 聊天 demo，而是把 Agent 接到了完整电商业务系统里。系统有三端角色、商品、购物车、订单、优惠、评价、鉴权、限流、日志、幂等、事务、库存预留、风控、文件存储和动态配置。Agent 的每个回答和动作都建立在这些真实业务能力之上。

## 10. 亮点九：AI Coding 工程化协作体系

### 10.1 解决的问题

本项目开发周期短、模块多，既包含 Go 后端、React 管理后台、Android 原生客户端，也包含 Agent Prompt、RAG、向量库、质量测评、链路追踪、动态配置、风控和三端业务闭环。如果只是把 AI 当成“代码生成器”，很容易出现几类问题：

- AI 在长周期项目里遗忘上下文，重复设计已经存在的能力。
- 改代码只解决表面问题，没有理解业务状态机，例如购物车、结算、支付、发货之间的边界。
- 新接口和前端解析不同步，导致后端能力已经有了但页面不能用。
- 为某个 bad case 写硬编码，短期看能过，长期破坏通用链路。
- Prompt、代码、测试、文档分散演进，后续团队成员和 AI 都难以判断当前系统真实约定。
- AI 修改速度很快，但如果没有验证 harness，就不知道这次修改是否破坏了别的链路。

所以本项目的 AI Coding 亮点不是“用了 AI 写代码”，而是围绕 AI Coding 建立了一套工程化协作方式：用 Spec 约束方向，用 Code Review 约束质量，用 Harness 验证结果，让 AI 参与需求拆解、设计、实现、排查、测试和文档迭代，但不让它脱离工程边界自由发挥。

### 10.2 Spec Coding：先建立项目 Spec，再驱动实现

项目初期就确定了 Spec Coding 的开发范式。我们没有直接从“写一个 AI 导购”开始堆代码，而是先把项目约定、需求边界、技术方案和接口协议沉淀到 `.ai` 目录下，让仓库本身成为 AI 和开发团队共同使用的项目上下文。

当前 `.ai` 文档体系大致分为：

- `.ai/prd/`：记录需求版本，例如基础导购需求、后端需求、Prompt 需求、质量体系需求。
- `.ai/tech/`：记录技术方案，例如 Agent 框架、RAG 设计、Milvus 接入、图片搜索、质量测评、动态配置、Android 技术方案。
- `.ai/api/`：记录接口文档和 Agent 输出协议，让前端、客户端和后端对齐数据结构。
- `.ai/spec/`：记录长期稳定的系统说明，例如系统分层、编码规范、文档规范和项目亮点材料。
- `.ai/review/`：记录代码检查、问题清单和专项排查结果。
- `.ai/skill/`：沉淀适用于本仓库的 code review skill。

这种方式的关键价值是：AI Coding 不再依赖某一次聊天上下文，而是有稳定、可读、可版本化的项目知识源。比如要改 Agent 输出协议时，不是只改后端 `runtime.go`，还要同步 `.ai/api/Agent输出协议_v1.md`；要改 RAG 检索链路时，需要先看 `.ai/tech/RAG设计_v5.md` 和相关测评方案；要改管理员页面，需要理解系统已经把平台管理、链路追踪、质量测评、Prompt 管理、风控管理拆成不同页面。

这套 Spec 也让 AI 更容易保持架构一致性。每次新增能力时，都可以先回答三个问题：

1. 这个需求属于哪个业务域或系统层？
2. 现有 Spec 里是否已经有类似约定？
3. 改完后哪些文档、接口、测试和测评数据需要同步？

从答辩角度可以这样讲：

> 我们把 AI Coding 从“聊天窗口里的临时上下文”迁移到了“仓库里的结构化 Spec”。Spec 既是人类团队的协作规范，也是 AI 的长期项目记忆。这样可以显著降低 AI 在复杂项目中遗忘约定、重复造轮子和破坏架构边界的风险。

### 10.3 Code Review：把 AI 输出纳入项目级质量约束

AI 生成代码的速度很快，但它天然缺少项目责任感。它可能让代码“看起来能跑”，但忽略真实业务系统最重要的约束，例如：

- 订单发货必须发生在支付后的 `pending_ship` 状态，而不是 checkout 后立即发货。
- Agent 说“已加购”必须真的调用 `add_cart_item` 并写入购物车。
- 商品推荐不能凭空生成商品名，挂品 `<item>` 必须是本轮工具返回的 product_id。
- 管理员页面不能把所有调试能力堆在一个页面里，需要按平台管理、调试观测、质量测评等职责拆分。
- Prompt 修改不能只改数据库，也要考虑默认配置、trace 可复现和管理端编辑。
- 新增接口如果涉及前后端协作，API 文档和输出协议必须同步。

因此我们在 `.ai/skill/xzxg-code-review/SKILL.md` 中沉淀了本项目专用的 Code Review 规则。这个 review skill 不是通用代码风格检查，而是面向本项目真实风险设计的审查清单。

重点包括：

- Agent 链路：是否真实调用工具，是否有 trace，是否存在模板话术假装完成动作。
- 商品真实性：商品推荐、挂品、购物车动作是否都来自真实商品 ID。
- RAG 和向量检索：召回、过滤、重排、弱相关处理是否可解释。
- 状态机：购物车、订单、支付、发货、评价、售后等状态是否符合业务闭环。
- 前后端协议：后端接口、SSE block、XML-like 标签、前端解析是否同步。
- 管理后台：是否能观测 prompt、模型原始输出、工具调用、检索片段和耗时。
- 文档同步：复杂链路是否有 `.ai/tech` 或 `.ai/api` 设计依据。
- 测评回归：新增核心能力是否补充正常 case 和边界 case。

这让 Code Review 从“看代码写得漂不漂亮”升级为“看 AI 生成的变更是否尊重项目系统性”。例如这类问题在 review 中会被明确指出：

- 为了一个 iPad case 写特殊逻辑，而不是用通用检索和重排解决。
- 非导购链路直接返回固定文案，没有调用真实业务工具。
- 测评脚本走的不是线上接口，导致测评结果和线上逻辑漂移。
- 管理端展示了 trace，但没有展示大模型输入 prompt 或工具返回的知识片段。

从答辩角度可以这样讲：

> 我们没有把 AI 生成代码视为最终结果，而是建立了项目级 Code Review Skill。它检查的不是简单格式，而是业务状态机、工具真实性、协议一致性、可观测性和可回归性。这样 AI 写得快，但仍然被项目工程质量约束住。

### 10.4 Harness：让 AI Coding 有可运行的验证闭环

AI Coding 最大的问题之一是“看起来改了，但不知道有没有真的改对”。所以本项目围绕 AI 生成代码建立了多层 harness，把修改结果放进真实系统中验证。

第一层是本地运行 harness。项目通过 Docker 和本地服务把中间件搭起来，包括：

- MySQL：保存账号、商品、订单、购物车、评价、trace、prompt 等核心数据。
- Redis：支撑缓存、限流或动态状态。
- Milvus：支撑商品、RAG、图片向量召回。
- MinIO：保存上传图片和文件。
- Nacos：承载部分动态配置和服务配置。
- Go 后端和 React 管理后台：本地可直接启动调试。

这意味着 AI 改完代码后，不只是跑编译，还可以直接启动前后端，走真实接口验证。例如：

- 上传图片后是否能在 MinIO 找到 object_key。
- 图片搜索工具是否能从 `/api/v1/files/file_xxx` 解析到 file_id。
- 加购是否真的写入购物车。
- checkout 是否创建待支付订单。
- 支付后是否进入待发货。
- 商家和管理员是否都能把 `pending_ship` 订单标记为已发货。

第二层是业务接口 harness。项目不是 mock 一个 Agent，而是把 Agent 接入真实电商业务域：

- 商品：查询、分页、商家管理、风险状态。
- 购物车：加购、改数量、删除、选中状态、优惠试算。
- 订单：checkout、支付、取消、确认收货、发货。
- 评价：查询、发布、商家回复、管理员审核。
- 优惠：可领券、已领券、促销、优惠试算。
- 文件：上传、读取、图片检索。

因此每次 AI Coding 修改都可以用真实业务行为验收，而不是只看最终文本。例如“发货功能能不能用”，不能只看页面按钮是否出现，而要看订单状态是否满足 `pending_ship`，点击后是否调用正确接口，后端是否真实更新订单，页面是否刷新状态，并在不可发货时说明“待用户支付”。

第三层是质量测评 harness。项目建设了多类可重复运行的测评：

- 意图识别测评：验证导购、非导购、服务域分类是否稳定。
- 商品召回测评：验证 RDS + 向量检索 + rerank 是否能召回真实商品。
- RAG 测评：验证非结构化知识切片和召回是否能命中证据。
- 图片搜索测评：验证图片向量生成、检索命中和响应耗时。
- Agent 端到端测评：验证从用户 query 到工具调用、回答和挂品是否符合预期。
- 无库存/无商品场景测评：验证模型不会硬挂无关商品。

更重要的是，bad case 会被沉淀成数据集。比如“推荐电脑，不要苹果”“华为电脑没有召回”“马桶商品库没有但模型挂了数码商品”“图片找外套但图片 URL 被当成本地路径”等问题，都可以从一次排查变成后续回归用例。

第四层是 trace harness。每次 Agent 请求都有 run_id，管理员端可以看到：

- planner 分类结果。
- 每次 LLM call 的实际 prompt。
- 模型原始输出。
- 工具调用参数。
- search_products / search_knowledge / search_image_products 的返回内容。
- 商品被过滤或弱相关的原因。
- 每一步耗时。
- 最终 SSE block 和文本输出。

这让 AI Coding 的调试方式从“猜模型为什么这么答”变成“复盘系统哪一层错了”。分类错就改 intent prompt 或测评数据；工具参数错就改 tool protocol；召回错就改 RAG/向量/重排；前端展示错就改协议解析；耗时长就看是模型、embedding、向量库还是异步摘要阻塞。

从答辩角度可以这样讲：

> Harness 的价值是把 AI Coding 的结果放进真实工程环境里验证。AI 不只是生成代码，还要通过本地中间件、真实接口、质量测评和链路追踪证明它没有破坏系统行为。

### 10.5 其他协作角度：让 AI 成为可管理的工程参与者

除了 Spec、Review 和 Harness，本项目还在协作方式上做了几件事。

第一是文档即上下文。`.ai` 目录不是附属材料，而是项目的工程记忆。需求、方案、接口、review、亮点表达都放在仓库里，AI 和人都围绕同一份上下文工作。这样即使换人、换分支、换模型，也能继续理解项目为什么这样设计。

第二是 bad case 驱动迭代。项目不是靠“感觉回答还行”推进，而是每次发现问题都追到 run_id，看 trace，判断是意图、prompt、工具、数据、前端协议还是状态机问题，然后把结论反哺到代码、prompt、测评数据或文档。

第三是人和 AI 分工明确。人负责判断业务边界、验收标准和方案取舍，例如“结算不属于购物车而属于订单创建”“不要为 iPad 写特殊逻辑”“非导购不能固定模板话术”。AI 负责快速实现、补测试、排查日志、维护文档和整理可复用表达。

第四是多分支并行开发。项目中不同方向通过 feature 分支推进，例如后端基础域、Android 原生客户端、质量测评、Prompt 管理、RAG、TTS/ASR、前端管理页等，降低 AI 大范围修改之间互相干扰的风险。

第五是从 Copilot 式补全升级到 Agentic Coding。AI 不只是补一段函数，而是参与完整工程链路：读 Spec、出设计、改代码、跑测试、查日志、重启服务、验证接口、更新文档、总结亮点。

### 10.6 为什么这是项目亮点

比赛项目里，很多团队会展示“我们用了 AI 辅助开发”。但这句话本身技术含量不高，因为 AI 写代码已经很常见。本项目更值得强调的是：我们把 AI Coding 本身也工程化了。

具体来说：

- Spec 解决“AI 不知道项目约定”的问题。
- Code Review 解决“AI 写得快但可能不可靠”的问题。
- Harness 解决“AI 改完不知道有没有真正确”的问题。
- Trace 和测评解决“AI 系统出错难复盘”的问题。
- 文档体系解决“长期迭代上下文丢失”的问题。

这和项目本身的 AI 导购系统形成了呼应：我们不仅在业务侧做了一个可控、可观测、可评测的 Agent，也在研发侧建立了可控、可观测、可评测的 AI Coding 流程。

### 10.7 这个亮点怎么讲

可以这样讲：

> 我们在项目研发过程中采用了 Spec Coding 的范式：先把需求、接口、系统分层、Prompt、RAG、质量测评和编码规范沉淀为仓库内 Spec，再让 AI 基于这些 Spec 参与实现。为了避免 AI 生成代码不可控，我们又建立了项目专用 Code Review Skill，重点审查业务状态机、真实工具调用、协议一致性、可观测性和测评回归。最后通过本地中间件、真实接口、管理员 trace 和质量测评 harness 验证每次修改。也就是说，AI 不只是帮我们写代码，而是被纳入了一套可追踪、可评审、可验证的工程流程。

## 11. 九个亮点之间如何串成一条主线

如果答辩时要串起来，可以按这条线讲：

1. 用户先表达需求，但需求可能是导购、交易、售后、优惠、闲聊，所以我们先做意图分类。
2. 意图确定后，主 Agent 根据意图动态拼接 Prompt、工具和 skill，而不是一个固定大 Prompt 包打天下。
3. 主 Agent 通过 ReAct 按需调用工具，尤其是商品推荐必须查真实商品库。
4. 真实商品召回采用 MySQL + Milvus 混合检索，并用否定语义、弱相关过滤和商品 ID 白名单控制幻觉。
5. 用户不只会打字，所以系统支持图片找同款和语音输入，把多模态也接入同一套工具体系。
6. 复杂链路会带来等待，所以通过 SSE、`<final>` 真流式、`content_delta` 和思考过程优化移动端体验。
7. AI 出错需要排查，所以管理员端提供全链路 trace，看到 prompt、模型输出、工具参数、召回片段和耗时。
8. 问题不能只靠人工感觉修，所以建设意图、RAG、Agent E2E、图片耗时等测评体系。
9. 最后，所有这些能力建立在真实电商基础链路上，包括三端、鉴权、限流、日志、事务、库存、风控和动态配置。
10. 研发过程本身也通过 Spec、Code Review 和 Harness 管理 AI Coding，让 AI 生成代码可追踪、可评审、可验证。

这条线的核心表达是：

```text
先走对链路
  -> 再动态组织能力
  -> 再查真实商品
  -> 再用多模态和流式体验服务用户
  -> 再用 trace 和测评持续改进
  -> 最后由生产化电商底座保障落地
  -> 同时用 Spec / Review / Harness 保障 AI Coding 本身可控
```

## 12. 答辩时可以重点讲的十句话

1. 我们做的不是聊天机器人，而是接入真实电商链路的 AI 导购系统。
2. 我们先用小模型做两层意图分类，让请求走对导购、交易、服务或闲聊链路。
3. 主 Agent 不是固定模板，而是根据意图动态拼接 Prompt、工具、skill 和输出范式。
4. 商品推荐必须先查真实商品库，模型不能凭空推荐。
5. 最终能挂出的商品卡必须来自本轮真实召回，并经过后端白名单校验。
6. 图片找同款不是独立 demo，而是作为 `search_image_products` tool 接入同一套 Agent 流程。
7. 我们用 SSE、`<final>` 和 `content_delta` 实现最终回答真流式、商品卡顺序插入和思考过程展示。
8. 管理员可以看到每次请求的 Prompt、模型原始输出、工具调用、RAG 片段、剔除原因和耗时。
9. bad case 会沉淀到测评数据集，通过意图、RAG、Agent E2E 和图片耗时测评形成回归闭环。
10. 我们也把 AI Coding 工程化，通过 Spec、Code Review 和 Harness 让 AI 参与开发但不脱离项目约束。

## 13. 当前还需要继续深化的点

### 12.1 Prompt 继续压缩

当前主 Agent Prompt 已经具备动态拼接能力，但仍有重复规则。后续应继续按以下结构压缩：

- 顶层身份和核心原则。
- 工具调用阶段。
- 最终输出阶段。
- 当前子意图范式。
- 当前工具策略。

目标是让模型每次只看到当前任务必要的信息。

### 12.2 非导购动作 intent 对齐

代码支持 `cart_add`、`cart_remove`、`cart_update_quantity`、`checkout_confirm` 等动作，但非导购 intent Prompt 中还需要明确补齐这些输出范围，让模型稳定识别可执行动作。

### 12.3 测评自动打分增强

后续可以继续补：

- ToolCallAccuracy。
- ToolArgQuality。
- Retrieval Hit@K / MRR / NDCG。
- Final groundedness。
- 图片请求 RT p50 / p90 / p99。
- bad case 自动归因。

### 12.4 Prompt 版本与 trace 绑定

Prompt 统一落库后，还应该把每次请求使用的 prompt version 写入 trace，方便复现“当时为什么这么答”。

## 14. 一句话总结

小猪小狗项目的核心亮点是：围绕真实电商交易场景，把大模型能力拆解为意图路由、动态编排、真实商品召回、多模态输入、流式交互、可观测排障、质量测评和生产化电商底座，同时把 AI Coding 研发过程本身工程化，形成一套可控、可信、可迭代的 AI 导购系统。
