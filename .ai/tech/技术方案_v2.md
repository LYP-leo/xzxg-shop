# 电商 AI 导购系统技术方案 v2

> 实现状态更新（2026-05-21）：`main` 已包含 Go 后端、React 客户端、Capacitor 原生壳、MySQL 数据库接入、三端登录、用户端导购、商家端商品管理和资料上传。Agent 主链路已接入 DashScope OpenAI 兼容接口，默认小模型 `qwen3.5-flash`、大模型 `qwen3.6-plus`，未配置 `DASHSCOPE_API_KEY` 时使用本地规则降级。动态配置中心采用 Nacos，模型、开关和 Agent 策略配置通过管理员接口动态修改。本文仍保留目标架构描述；与目标架构相比，Qdrant/Milvus 向量检索、Redis 分布式限流、RocketMQ、管理员评测闭环仍待落地。

## 1. 方案目标

本方案基于 PRD v1、技术方案 v1、Agent 框架 v2 和 `v2_问题.md` 重新整理，目标是形成一份可以直接指导落地开发的 v2 技术方案。v2 重点解决：

- 会话模型如何实现。
- 主链路中所有 LLM 调用的输入、输出和 Prompt。
- 流式输出中前端如何实时解析结构化内容。
- RAG 文档如何解析、清洗、递归切片、Embedding、召回和重排。
- Agent 工具有哪些，每个工具的输入输出是什么。
- 系统其余模块如何落地，包括数据模型、接口、异步任务、目录结构、评测和部署。

v2 核心链路：

```text
用户进入聊天窗口
  -> 创建元会话 chat_session
  -> 用户发送一次问题 user_message
  -> Agent Runtime 执行
  -> 多次 LLM 调用写 assistant_message 日志
  -> 主 Agent 以 XML 标签流式输出
  -> 后端解析 XML 标签并实时转换为 SSE
  -> 前端渲染文本、商品卡片、对比表、引用、追问
  -> 保存最终会话输出和 Trace
```

## 2. 技术栈

后端：

- Go 1.22+
- 当前实现：标准库 `net/http` + `database/sql` + MySQL driver
- 目标演进：可按复杂度评估是否引入 Gin/go-chi 和 GORM
- Redis
- Nacos 配置中心
- RocketMQ
- Qdrant 向量数据库

前端：

- React + TypeScript
- Zustand 或 React Context
- Fetch + SSE

AI：

- Chat LLM：意图识别、Query 改写、主回答、追问生成、评测评分
- 当前实现：通过 DashScope OpenAI 兼容接口调用，`qwen3.5-flash` 用于 Planner/追问，`qwen3.6-plus` 用于复杂导购回答。
- Embedding：文本 chunk 向量化、Query 向量化
- Vision LLM：图片内容理解
- OCR：图片文字识别，可由 Vision 模型兼任

部署：

- Docker Compose
- 服务：frontend、api、worker、mysql、nacos、redis、rocketmq、qdrant

当前本地状态：

- MySQL 已可用并被后端使用。
- Nacos 已作为动态配置中心接入后端，Compose 已增加 Nacos standalone 服务。
- Redis、RocketMQ、Qdrant 已在 compose 方向规划，但本机 Docker daemon 拉取镜像存在网络阻塞，尚未完整启动。

当前基础体系生产化落地：

- HTTP 中间件已包含 `request_id`、结构化访问日志、CORS、请求体大小限制、进程内限流、统一鉴权与角色权限。
- 用户端接口要求 `user` 角色，商家端接口要求 `merchant` 角色，管理员接口要求 `admin` 角色。
- 错误响应统一包含 `code`、`message`、`request_id`。
- 用户端购物车、会话、消息、Agent run 已按 `account_id` 隔离。
- 用户端已支持购物车结算生成订单、订单列表。
- 商家端已支持查看订单、发货、商品删除。
- 管理员端已支持账号列表/启停、商品列表/下架、订单列表、文档列表。
- 当前限流为单进程内存实现，生产部署时需要替换为 Redis 分布式限流。

当前 Agent 主链路落地：

- 用户消息进入 `POST /api/v1/agent/sessions/{session_id}/messages:stream`。
- 后端创建 `user_message` 与 `agent_run`。
- 使用小模型 `qwen3.5-flash` 进行意图规划，输出 `intent`、`answer_mode`、关键词和是否需要对比。
- 调用本地商品检索与资料检索工具，形成候选商品和引用上下文。
- 根据 Planner 结果选择 `qwen3.5-flash` 或 `qwen3.6-plus` 生成主回答。
- 使用小模型生成追问。
- 通过 SSE 输出 `message_start`、`status`、`text_delta`、`block_delta`、`followups`、`message_end`。
- Agent trace 已落表到 `agent_trace_events`，可通过 `GET /api/v1/agent/runs/{run_id}/trace` 查询一次 run 的 planner、工具检索、回答模型、追问模型和完成事件。

## 3. 核心架构

```text
客户端交互层
  -> API 接入层
  -> Agent 编排层
  -> 工具服务层
  -> 数据与知识层
  -> 评测反馈层
```

### 3.1 客户端交互层

职责：

- 创建新聊天窗口。
- 发送文本或图片消息。
- 接收 SSE 流。
- 实时解析 XML 派生事件。
- 渲染文本、商品卡片、商品对比表、引用来源、追问建议。
- 支持停止生成、重新生成、查看历史元会话。

### 3.2 API 接入层

职责：

- 创建 `chat_session`。
- 接收用户消息并创建 `user_message`。
- 启动 Agent Runtime。
- 将 Agent Runtime 的事件转换为 SSE。
- 取消生成。
- 查询会话详情和执行详情。

### 3.3 Agent 编排层

职责：

- 整理多模态输入。
- 构建当前元会话上下文。
- Query 改写。
- 意图识别。
- 工具规划。
- 工具执行。
- 动态拼接主 Agent Prompt。
- 流式调用主 Agent。
- 解析主 Agent XML 输出。
- 调用追问 LLM。
- 记录 Trace。

### 3.4 工具服务层

工具：

- `parse_image`
- `rewrite_query`
- `classify_intent`
- `search_products`
- `resolve_products`
- `compare_products`
- `search_knowledge`
- `rank_products`
- `build_product_cards`

- `generate_followups`

### 3.5 数据与知识层

数据：

- MySQL：业务数据、会话、消息、文档、评测、日志。
- Redis：限流、临时流式状态、会话执行锁。
- Milvus：文本向量、图片向量。
- MinIO：上传文件和图片。

### 3.6 评测反馈层

职责：

- 维护评测集。

## 4. 会话模型

当前实现说明：

- 已落地 `chat_sessions`、`user_messages`、`agent_runs`。
- 当前尚未落地 `assistant_messages` 调用日志表，Agent Runtime 仍为演示版流式生成。
- 会话、消息、Agent run 和购物车已按 `account_id` 隔离。

### 4.1 概念定义

v2 使用三个核心表：

```text
chat_session      元会话 / 对话组
user_message      一次用户问题
assistant_message 一次 LLM 调用日志
```

定义：

- 一个 `chat_session` 是一个聊天窗口或一次元会话。
- 一个 `chat_session` 中可以包含多次 `user_message`。
- 一个 `user_message` 是用户发起的一次问题。
- 一个 `user_message` 的 Agent 执行过程中可能发生多次 LLM 调用，每次调用记录一条 `assistant_message`。
- `assistant_message` 不承担流式状态管理，只在 LLM 调用结束后记录日志。
- 当前窗口最终展示内容保存在 `user_message.final_output` 和 `chat_session.output_snapshot` 中。

### 4.2 为什么 assistant_message 不需要状态

`assistant_message` 是 LLM 调用日志，不是前端消息状态机。它只在一次 LLM 调用完成后落库，用于：

- 查看执行详情。
- Trace 回放。
- Prompt 调试。
- 评测复盘。
- 成本统计。

流式过程中的临时状态不落 `assistant_message.status`，而由以下机制处理：

- HTTP 连接和 SSE 控制实时输出。
- Redis 记录 `stream:{run_id}:cancel` 和 `stream:{run_id}:buffer`。
- `agent_runs` 记录一次 Agent 执行的最终状态。

### 4.3 一次请求的数据写入顺序

```text
用户进入聊天窗口
  -> 创建 chat_session

用户发送问题
  -> 创建 user_message
  -> 创建 agent_run(status=running)
  -> Agent Runtime 执行
  -> 每次 LLM 调用结束后写 assistant_message
  -> 流式输出过程中更新 Redis 临时 buffer
  -> 生成完成后更新 user_message.final_output
  -> 更新 agent_run(status=completed)
  -> 更新 chat_session.output_snapshot
```

## 5. Agent 主链路

### 5.1 主流程

```text
1. Message Intake
2. Input Normalize
3. Context Build
4. Query Rewrite LLM
5. Intent Classify LLM
6. Tool Plan
7. Tool Execute
8. Prompt Build
9. Main Agent LLM Streaming
10. XML Stream Parser
11. Tool Result Enrich
12. Followup LLM
13. Final Output Persist
14. Trace Persist
```

### 5.2 链路说明

#### Message Intake

输入：

- `session_id`
- `content`
- `attachments`
- `client_message_id`

输出：

- `user_message`
- `agent_run`

动作：

- 校验 session 是否存在。
- 创建 `user_message`。
- 创建 `agent_run(status=running)`。
- 初始化 Trace。

#### Input Normalize

动作：

- 去除多余空格。
- 限制输入长度。
- 附件安全校验。
- 图片进入 `parse_image`。

#### Context Build

只读取当前 `chat_session` 下的上下文：

- 最近 5 条 `user_message`。
- 每条消息的最终输出摘要。
- 最近推荐商品 ID。
- 最近对比商品 ID。
- 当前 session summary。

#### Query Rewrite LLM

显式处理省略、指代、多轮继承。

#### Intent Classify LLM

输出主意图、二级场景和槽位。

#### Tool Plan

根据意图选择固定工具链，不让模型自由决定工具。

#### Tool Execute

执行商品检索、知识检索、商品对比、图片相似召回等。

#### Prompt Build

根据意图和工具结果动态拼接主 Agent Prompt。

#### Main Agent LLM Streaming

主 Agent 负责流式输出 XML。

#### XML Stream Parser

后端增量解析 XML 标签，将完整标签转换为结构化 SSE 事件。

#### Followup LLM

主回答完成后，单独调用追问 LLM 生成 2 到 3 个追问。

### 6.1 Query Rewrite LLM

Prompt 文件：

```text
backend/prompts/query_rewrite_v2.md
```

输入：

```json
{
  "current_query": "那第一款怎么样？",
  "session_context": [
    {
      "role": "user",
      "content": "我主要给老人用，不要太贵"
    },
    {
      "role": "assistant",
      "summary": "推荐了 A 手机、B 手机，A 手机排第一"
    }
  ],
  "recent_products": [
    {
      "rank": 1,
      "product_id": "p_a",
      "name": "A 手机"
    }
  ]
}
```

输出：

```json
{
  "rewritten_query": "A 手机是否适合老人使用？请结合价格、易用性、屏幕、续航和售后风险分析。",
  "resolved_refs": [
    {
      "raw_text": "第一款",
      "ref_type": "product",
      "product_id": "p_a"
    }
  ],
  "inherited_constraints": {
    "target_user": "老人",
    "price_preference": "不要太贵"
  },
  "confidence": 0.9
}
```

约束：

- 不回答用户问题。
- 只做改写和指代解析。
- 无法解析指代时 `resolved_refs` 为空，并保留原 query。

## 8. XML 流式输出协议

### 8.1 为什么用 XML

JSON 不适合模型逐字流式生成时实时解析，因为：

- JSON 必须整体闭合后才能可靠解析。
- 嵌套数组和转义容易在流中间处于非法状态。
- 前端无法在 JSON 完整前稳定识别结构化块。

XML 标签更适合流式：

- 文本可以先输出。
- 标签闭合后立刻解析对应 block。
- 商品卡片、引用、对比表可以分块输出。
- 容错更简单，未闭合标签可以等待后续 delta。

### 8.2 主 Agent XML 输出规范

主 Agent 允许输出以下标签：

```xml
<answer>
  <text>自然语言回答片段</text>
  <product_card product_id="p_001" rank="1">
    <reason>推荐理由</reason>
    <risk>风险提示</risk>
  </product_card>
  <comparison>
    <row product_id="p_001" field="适合人群">拍娃、预算敏感</row>
  </comparison>
  <citation chunk_id="ck_001">支持该结论的证据说明</citation>
  <warning code="no_evidence">知识库没有找到明确活动规则</warning>
</answer>
```

规则：

- `<text>` 可出现多次，按顺序拼接为主文本。
- `<product_card>` 只允许输出 `product_id`、`rank`、`reason`、`risk`，商品名、价格、图片由后端查询商品服务补全。
- `<citation>` 必须引用真实 `chunk_id`。
- `<warning>` 用于无证据、低置信度或降级说明。
- 追问不由主 Agent 输出，统一由 Followup LLM 输出。

### 8.3 SSE 事件

后端解析 XML 后推送 SSE。

```text
event: message_start
data: {"run_id":"run_001","session_id":"sess_001","message_id":"msg_001"}

event: text_delta
data: {"delta":"如果预算在3000以内，"}

event: block_delta
data: {"type":"product_card","product":{"product_id":"p_001","name":"X Phone","price":"2999.00","reason":"..."}}

event: block_delta
data: {"type":"citation","citation":{"chunk_id":"ck_001","title":"商品详情","snippet":"..."}}

event: followups
data: {"questions":["更重视拍照还是续航？"]}

event: message_end
data: {"run_id":"run_001"}
```

### 8.4 后端 XML 增量解析

后端维护一个 `xml_buffer`：

```text
收到 LLM delta
  -> 追加到 xml_buffer
  -> 扫描是否出现完整闭合标签
  -> 完整 <text> 立即转 text_delta
  -> 完整 <product_card> 查询商品服务后转 block_delta
  -> 完整 <citation> 查询 chunk 元数据后转 block_delta
  -> 未闭合标签继续等待
```

容错：

- 标签不合法：写 Trace，降级为普通文本。
- `product_id` 不存在：不发商品卡片，发送 warning。
- `chunk_id` 不存在：不发引用，记录 no_citation。
- 流结束后仍有未闭合标签：尝试补闭合；失败则按文本输出。

## 10. RAG 构建方案

### 10.1 异步流程

```text
上传文档
  -> documents.status = uploaded
  -> RocketMQ document.parse
  -> Worker Parse
  -> Worker Clean
  -> Worker Recursive Segment
  -> knowledge_chunks 写 MySQL
  -> RocketMQ document.embed
  -> Worker Embedding
  -> 写 Qdrant
  -> documents.status = indexed
```

### 10.2 解析

| 文件类型 | 解析策略 |
| --- | --- |
| `.md` | 按标题层级和段落解析 |
| `.txt` | 按空行、标点和长度解析 |
| `.pdf` | 提取文本、页码、表格；扫描件走 OCR |
| `.docx` | 标题、段落、表格 |
| `.html` | 正文抽取，删除导航脚本样式 |
| 图片 | OCR + Vision |

### 10.3 清洗

规则：

- 删除页眉页脚。
- 删除重复版权和导航。
- 合并多余空格。
- 保留标题层级。
- 保留型号、价格、时间、适用条件。
- 表格每行补全表头。

### 10.4 递归切片

切片不是简单固定长度，而是递归按语义边界切。

分隔优先级：

```text
一级标题 #
  -> 二级标题 ##
  -> 三级标题 ###
  -> 空行
  -> 句号/问号/感叹号/分号
  -> 逗号/顿号
  -> 固定长度兜底
```

算法：

```text
recursive_split(text, separators, max_len, min_len):
  if len(text) <= max_len:
    return [text]
  sep = first separator that can split text into useful parts
  if no sep:
    return fixed_length_split(text, max_len, overlap)
  parts = split by sep
  merge parts until close to max_len
  for each merged part:
    if len(part) > max_len:
      recursive_split(part, next separators)
    else:
      keep part
```

参数：

- `max_len`: 800 中文字符
- `min_len`: 120 中文字符
- `overlap`: 80 到 120 中文字符
- 表格和 FAQ 使用专用切片，不强行按字符截断。

特殊切片：

- FAQ：一问一答为一个 chunk。
- 活动规则：按活动名称、适用条件、叠加限制、生效时间切。
- 商品参数：同一商品的参数表尽量保持在同一个 chunk 或相邻 chunk。
- 售后政策：按服务类型和例外条件切。

### 10.5 元数据

每个 chunk 必须保存：

```json
{
  "document_id": "doc_001",
  "chunk_id": "ck_001",
  "doc_type": "promotion",
  "title_path": ["618 活动", "会员券规则"],
  "product_id": "p_001",
  "category": "手机",
  "brand": "X",
  "source_page": 2,
  "effective_start": "2026-05-01T00:00:00+08:00",
  "effective_end": "2026-06-20T23:59:59+08:00",
  "content_hash": "sha256"
}
```

### 10.6 召回

在线检索：

```text
rewritten_query
  -> query embedding
  -> vector search top 30
  -> keyword search top 30
  -> metadata filter
  -> merge deduplicate
  -> rerank top 8
  -> evidence compress
```

关键词检索字段：

- 标题。
- chunk 内容。
- 商品名。
- 品牌。
- 活动名。
- 参数名。

Rerank 特征：

- Query 与 chunk 语义相关性。
- 是否匹配意图 `doc_type`。
- 是否匹配商品 ID。
- 是否在有效期内。
- 是否包含关键事实词。

- 意图识别失败。
- 商品检索失败。
- RAG 未命中。
- 主 Agent 编造。
- XML 格式错误。
- 卡片补全失败。
- 追问无关。

## 15. 错误处理

错误码：

| code | 说明 |
| --- | --- |
| `invalid_argument` | 参数错误 |
| `session_not_found` | 会话不存在 |
| `attachment_invalid` | 附件不合法 |
| `llm_error` | LLM 调用失败 |
| `vision_error` | 图片解析失败 |
| `knowledge_error` | 知识库检索失败 |
| `product_error` | 商品服务失败 |
| `xml_parse_error` | XML 解析失败 |
| `stream_canceled` | 用户取消 |
| `internal_error` | 内部错误 |

降级：

- Query Rewrite 失败：使用原始 Query。
- Intent 失败：进入 `general_shopping_chat`。
- 图片解析失败：提示图片无法识别，继续处理文本。
- 商品服务失败：只输出知识回答，不发商品卡片。
- RAG 失败：不输出确定参数或规则。
- XML 解析失败：降级为纯文本。

## 16. 缓存与 Redis Key

```text
rate:user:{user_id}:chat
stream:{run_id}:cancel
stream:{run_id}:buffer
lock:session:{session_id}:run
product:detail:{product_id}
knowledge:query:{query_hash}
```

说明：

- `stream:{run_id}:cancel` 用于停止生成。
- `stream:{run_id}:buffer` 用于短期保存未完成流式内容。
- `lock:session:{session_id}:run` 防止同一会话并发生成冲突。

## 22. 后端接口细化

本项目重点是 Agent，不做完整电商交易平台，但需要具备最小电商域能力，确保 Agent 推荐、商品卡片、购物车和商家资料都有真实数据来源。

后端领域边界：


### 24.5 SSE 客户端解析

前端只解析后端 SSE 事件，不直接解析主 Agent XML。XML 解析由后端完成。

前端事件处理：

```ts
function handleAgentEvent(event: AgentSseEvent) {
  switch (event.type) {
    case 'message_start':
      createStreamingTurn(event.session_id, event.user_message_id, event.run_id);
      break;
    case 'status':
      updateTurnStatusText(event.run_id, event.text);
      break;
    case 'text_delta':
      appendTurnText(event.run_id, event.delta);
      break;
    case 'block_delta':
      appendTurnBlock(event.run_id, event.block);
      break;
    case 'followups':
      setTurnFollowups(event.run_id, event.questions);
      break;
    case 'message_end':
      completeTurn(event.run_id, event.final_output);
      break;
    case 'error':
      failTurn(event.run_id, event.message);
      break;
  }
}
```

SSE 连接状态：

| 状态 | UI 表现 |
| --- | --- |
| connecting | 输入框上方展示“正在连接” |
| streaming | 展示停止按钮，禁用重复发送 |
| completed | 恢复输入 |
| failed | 展示重试按钮 |
| canceled | 展示“已停止生成” |
