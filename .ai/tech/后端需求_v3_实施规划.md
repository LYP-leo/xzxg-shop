# 后端需求 v3 实施规划

## 需求来源

来自 `.ai/prd/后端需求_v3.md`：

1. 会话模块：历史会话查询，每个历史会话需要简介/名字，可在压缩会话时写入会话表。
2. 订单：虚拟支付、超时失效等基础订单能力。
3. 优惠：平台优惠、商家优惠、优惠券逻辑模拟。
4. 评价：实现评价模块。
5. tools 实现：结合现有功能改造 RAG 模块，提供需要的 tools。
6. 文档：梳理现有接口文档，更新过程中随时更新。

## 当前能力盘点

### 已有

- 用户/商家/管理员账号体系与鉴权。
- 商品、分类、SKU、购物车。
- 用户订单列表、商家订单列表、管理员订单列表。
- 从购物车创建订单。
- 商家修改订单状态。
- Agent 会话、消息、run、trace。
- 知识文档、chunk、基础 RAG 检索。
- Nacos 动态配置和 prompt 配置。

### 主要缺口

- 会话没有稳定的 title/summary 维护策略。
- 订单缺少支付态、支付单、支付超时、取消、关闭、退款/售后状态。
- 优惠域没有数据模型、计算流程、券领取/核销。
- 评价域没有评价表、接口、商品评分汇总。
- Agent tools 目前主要是内置搜索/购物车动作，没有统一 tool registry、参数 schema、trace 结果。
- 接口文档分散，前端联调缺少统一 API 文档。

## 总体实施顺序

建议按“基础数据域 -> Agent tools -> 前端联调文档”的顺序做，避免 Agent 先调用不存在的能力。

1. 会话模块补全。
2. 订单与虚拟支付。
3. 优惠体系。
4. 评价体系。
5. 非导购/导购 tools 与 RAG 改造。
6. API 文档和测试数据补齐。

## Phase 1：会话模块

### 目标

历史会话列表可用于前端展示，支持用户看到会话标题、简介、最近消息时间和消息数量。

### 数据模型

扩展 `agent_sessions`：

- `title`：会话标题，默认由首条用户消息生成。
- `summary`：会话摘要，由对话压缩/总结写入。
- `last_message_at`：最近消息时间。
- `message_count`：消息数量。
- `archived_at`：归档时间，可选。

### 接口

- `GET /api/v1/agent/sessions`
  - 返回当前用户会话列表。
  - 字段：`session_id/title/summary/last_message_at/message_count/created_at/updated_at`。
- `GET /api/v1/agent/sessions/{session_id}/messages`
  - 已有或补齐消息分页。
- `PATCH /api/v1/agent/sessions/{session_id}`
  - 修改标题、归档。

### Agent 集成

- 首轮消息后，如果 title 为空，用规则或小模型生成 10-20 字标题。
- 每轮结束后更新 `last_message_at/message_count`。
- 对话压缩时写 `summary`。

## Phase 2：订单与虚拟支付

### 目标

从“购物车直接生成待发货订单”升级为标准模拟订单流：

```text
购物车确认
  -> 创建待支付订单 pending_payment
  -> 创建虚拟支付单 payment_pending
  -> 用户支付成功 paid / 支付失败 failed
  -> 超时关闭 closed_timeout
  -> 商家发货 shipped
  -> 用户确认收货 completed
  -> 可评价
```

### 数据模型

扩展 `orders`：

- `order_no`
- `status`
  - `pending_payment`
  - `paid`
  - `pending_ship`
  - `shipped`
  - `completed`
  - `closed_timeout`
  - `canceled`
  - `refund_requested`
  - `refunded`
- `total_amount`
- `discount_amount`
- `pay_amount`
- `payment_deadline_at`
- `paid_at`
- `closed_at`
- `completed_at`
- `cancel_reason`

新增 `payments`：

- `payment_id`
- `order_id`
- `account_id`
- `amount`
- `status`: `pending/success/failed/expired/refunded`
- `method`: `mock_balance/mock_wechat/mock_alipay`
- `transaction_no`
- `expires_at`
- `paid_at`
- `created_at/updated_at`

### 接口

- `POST /api/v1/orders:checkout`
  - 从购物车创建待支付订单，返回订单和支付截止时间。
- `POST /api/v1/orders/{order_id}:pay`
  - 虚拟支付成功。
- `POST /api/v1/orders/{order_id}:cancel`
  - 用户取消未支付订单。
- `POST /api/v1/orders/{order_id}:confirm-receipt`
  - 用户确认收货。
- `POST /api/v1/admin/orders:expire`
  - 或后台定时任务：关闭超时未支付订单。
- `GET /api/v1/orders/{order_id}`
  - 订单详情。

### 实现策略

- MVP 不做真实支付，只做状态机和金额冻结模拟。
- 每次查询/支付/创建订单前调用 `ExpirePendingOrders(now)`，懒执行关闭超时订单。
- 订单状态转换必须集中校验，避免任意 PATCH。
- 商家只能处理自己订单，管理员可查看全部订单。

## Phase 3：优惠体系

### 目标

支持平台优惠、商家优惠、优惠券三类，并可在购物车/订单确认页计算折扣。

### 优惠类型

1. 平台优惠：
   - 全场满减。
   - 指定分类满减。
   - 新人券/平台券。
2. 商家优惠：
   - 单商家满减。
   - 指定商品折扣。
   - 店铺券。
3. 用户优惠券：
   - 领取。
   - 可用/不可用判断。
   - 下单核销。

### 数据模型

新增：

- `promotion_rules`
  - `promotion_id`
  - `scope`: `platform/merchant/product/category`
  - `merchant_id/product_id/category_id`
  - `type`: `full_reduction/percentage/fixed_amount/free_shipping`
  - `threshold_amount`
  - `discount_amount`
  - `discount_rate`
  - `stackable`
  - `start_at/end_at`
  - `status`
- `coupons`
  - `coupon_id`
  - `name`
  - `scope`
  - `type`
  - `threshold_amount`
  - `discount_amount`
  - `total_count`
  - `per_user_limit`
  - `start_at/end_at`
  - `status`
- `user_coupons`
  - `user_coupon_id`
  - `coupon_id`
  - `account_id`
  - `status`: `unused/used/expired`
  - `claimed_at/used_at`
  - `order_id`

### 接口

用户端：

- `GET /api/v1/promotions`
- `GET /api/v1/coupons/available`
- `POST /api/v1/coupons/{coupon_id}:claim`
- `GET /api/v1/cart/discount-preview`
- `POST /api/v1/orders:checkout` 支持 `user_coupon_ids`

商家端：

- `GET /api/v1/merchant/promotions`
- `POST /api/v1/merchant/promotions`
- `PATCH /api/v1/merchant/promotions/{promotion_id}`

管理员端：

- `GET /api/v1/admin/promotions`
- `POST /api/v1/admin/promotions`

### 折扣计算顺序

MVP 建议：

1. 商品原价合计。
2. 商家优惠，按商家分组计算。
3. 平台优惠。
4. 用户券。
5. 得到 `discount_amount/pay_amount`。

每一步输出 `discount_breakdown`，前端和 Agent 都能展示。

## Phase 4：评价模块

### 目标

用户完成订单后可评价商品；商品详情和 Agent 可读取评分、评价摘要和风险点。

### 数据模型

新增 `product_reviews`：

- `review_id`
- `order_id`
- `order_item_id`
- `product_id`
- `sku_id`
- `account_id`
- `rating` 1-5
- `content`
- `images_json`
- `tags_json`
- `status`: `visible/hidden/deleted`
- `merchant_reply`
- `merchant_replied_at`
- `created_at/updated_at`

可选新增 `product_review_stats`：

- `product_id`
- `rating_avg`
- `rating_count`
- `tag_summary_json`
- `updated_at`

### 接口

用户端：

- `GET /api/v1/products/{product_id}/reviews`
- `POST /api/v1/orders/{order_id}/items/{order_item_id}/review`
- `PATCH /api/v1/reviews/{review_id}`
- `DELETE /api/v1/reviews/{review_id}`

商家端：

- `GET /api/v1/merchant/reviews`
- `POST /api/v1/merchant/reviews/{review_id}:reply`

管理员端：

- `GET /api/v1/admin/reviews`
- `PATCH /api/v1/admin/reviews/{review_id}/status`

### 规则

- 只有 `completed` 订单可评价。
- 同一订单项只能评价一次。
- 商家只能回复自己商品的评价。
- 管理员可隐藏违规评价。

## Phase 5：Agent tools 与 RAG 改造

### 目标

把订单、优惠、评价、售后规则等能力暴露成 Agent 可调用 tools，使导购和非导购都能使用真实数据。

### Tool Registry

新增统一 tool 定义：

```go
type AgentTool struct {
  Name        string
  Description string
  InputSchema any
  Handler     ToolHandler
}
```

MVP tools：

- `product.search`
- `product.detail`
- `cart.get`
- `cart.add`
- `order.list`
- `order.detail`
- `order.pay`
- `order.cancel`
- `coupon.available`
- `coupon.claim`
- `promotion.explain`
- `review.list`
- `review.summary`
- `policy.search`

### RAG 改造

当前 RAG 主要是 `SearchKnowledge(query)`，建议升级为：

1. 按意图选择检索域：
   - 导购：商品详情、导购话术、评价摘要。
   - 优惠：活动规则、优惠券规则。
   - 售后：售后政策、FAQ。
   - 评价：评价摘要、评论 chunk。
2. 检索结果带 `source_type`：
   - `product_doc`
   - `promotion_rule`
   - `after_sales_policy`
   - `faq`
   - `review_summary`
3. 回答时强制引用证据 ID。
4. tool 调用和 RAG 检索都写入 trace。

### Agent 链路

- `guide`：继续走导购链路，但可调用优惠、评价、政策 tools 增强回答。
- `fast_product`：继续确定性购物车/订单动作。
- `non_guide`：按《非导购Agent策略链路设计_v1》接二级意图和 tools。

## Phase 6：接口文档

### 目标

给前端同学一份稳定接口文档，避免联调靠猜。

### 文档位置

建议新增：

- `.ai/api/API接口文档_v3.md`
- `.ai/api/API变更记录.md`

### 文档格式

每个接口写：

- 方法与路径。
- 权限角色。
- 请求参数。
- 响应示例。
- 错误码。
- 前端展示建议。
- 是否已实现。

## 里程碑建议

### M1：会话 + 订单状态机

- 会话 title/summary。
- 订单待支付、支付、超时关闭、取消、确认收货。
- 订单接口文档。

### M2：优惠 MVP

- 平台/商家优惠规则表。
- 用户券领取和可用券查询。
- 购物车/下单折扣预览。
- Agent 可查询优惠。

### M3：评价 MVP

- 完成订单后评价。
- 商品评价列表和评分统计。
- 商家回复、管理员隐藏。
- Agent 可读评价摘要。

### M4：Agent tools + RAG

- tool registry。
- 非导购二级链路。
- RAG 按 source_type 检索。
- trace 完整落表。

## 优先级

P0：

- 订单支付状态机。
- 订单超时关闭。
- 会话标题/摘要。
- 接口文档骨架。

P1：

- 优惠券领取/核销。
- 折扣预览。
- 评价创建/列表。
- Agent order/coupon/review tools。

P2：

- 商家促销管理。
- 管理员评价审核。
- 售后/活动规则 RAG 精细化。
- 价格监控、复购等非导购增强。

## 风险与约束

- 优惠计算容易和订单金额不一致，必须让 checkout 使用同一套 discount engine。
- 订单状态不能散落在 handler 中硬改，需要集中状态机。
- 评价必须绑定已完成订单项，避免刷评价。
- Agent 不能直接编造优惠、售后和物流结果，必须通过 tools 或知识库证据。
- 文档必须和接口同步更新，否则前端联调成本会快速上升。
