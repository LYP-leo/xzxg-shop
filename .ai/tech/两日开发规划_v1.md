# 两日开发规划 v1

> 状态更新：截至 2026-05-20，本规划中的两日初步演示目标已经合入 `main`。当前实现已超过原计划中的 mock 骨架阶段，后端已接 MySQL，前端已补三端角色入口，商家端已支持商品管理和资料上传。

## 1. 目标

两天内交付一个可演示的初步方案，而不是完整商业系统。初步方案必须跑通主链路：

```text
前端聊天页
  -> 创建会话
  -> 发送用户问题
  -> 后端 Agent Runtime
  -> 商品检索和知识检索 mock/最小实现
  -> SSE 流式返回文本和商品卡片
  -> 前端实时渲染
```

两天结束时应具备：

- React 聊天页可用，支持文本输入、流式回复、商品卡片展示。
- Go 后端可启动，提供会话、消息、SSE 聊天接口。
- Agent 主链路有清晰代码骨架，可先使用 mock LLM 和 mock 商品数据。
- RAG/知识库链路有接口和数据模型，第一版可先用本地文档或 mock chunk。
- Docker Compose 有基础服务定义，便于后续接 MySQL、Redis、Qdrant。
- 评测闭环有最小 case 文件和评测命令骨架。

当前已完成：

- React 客户端可运行，支持用户端 AI 导购、商品、购物车。
- Capacitor iOS/Android 原生壳已生成。
- Go 后端可运行，提供健康检查、认证、商品、购物车、商家管理、Agent SSE 接口。
- MySQL 已接入，商品、知识 chunk、账号、会话、消息、run、购物车均落库。
- 商家端可新增/编辑商品，上传商品资料后写入 `knowledge_documents` 和 `knowledge_chunks`。
- 三端登录已完成：用户、商家、管理员。

当前未完成或仍为雏形：

- Agent Runtime 仍是规则化/演示版，尚未接真实 LLM。
- RAG 仍是 MySQL chunk 检索兜底，尚未接 Qdrant embedding 召回和重排。
- Redis、RocketMQ、Qdrant 的 Docker 部署受本机镜像拉取问题阻塞。
- 管理员评测闭环仍是页面雏形，缺真实评测运行和报告接口。

## 2. 两天排期

### Day 1：搭骨架，打通前后端

后端目标：

- 初始化 Go 项目目录。
- 建立 API 路由：健康检查、创建会话、发送消息 SSE、取消生成。
- 建立核心类型：`ChatSession`、`UserMessage`、`AgentRun`、`AgentResponse`、`SSEEvent`。
- 实现 mock Agent Runtime：输入用户问题，流式输出文本，再输出一个 mock 商品卡片。
- 准备 mock 商品数据和 mock 知识 chunk。

前端目标：

- 初始化 React + TypeScript 项目。
- 实现聊天主页面。
- 支持创建会话、发送消息、接收 SSE。
- 支持 `text_delta` 和 `block_delta` 两类事件渲染。
- 实现商品卡片组件。

对齐点：

- 下午前固定 SSE 协议。
- 晚上前完成前后端联调：输入一句问题，前端能看到流式文本和商品卡片。

### Day 2：补 Agent/RAG/评测雏形，形成演示闭环

后端目标：

- 拆分 Agent Runtime 结构：Context Builder、Intent Router、Tool Executor、Response Composer。
- 增加商品检索工具：先从 mock 商品表筛选，后续替换 MySQL。
- 增加知识检索工具：先从本地 mock chunk 检索，后续替换 Qdrant + MySQL。
- 增加 Trace 结构，记录 query、intent、tool results、final response。
- 增加文档上传接口骨架，可先只落本地文件和状态记录。

前端目标：

- 增加消息状态：生成中、完成、失败、取消。
- 增加停止生成按钮。
- 增加引用来源和追问建议展示。
- 优化移动端布局，保证演示时体验稳定。

评测目标：

- 新增 5 到 10 条典型导购 case。
- 新增最小评测脚本或接口，能批量调用 mock Agent 并输出结果 JSON。

对齐点：

- 中午前固定 `AgentResponse` 字段。
- 晚上前完成一次端到端演示：推荐、对比或规则解释至少跑通一个场景。

交付标准：

- `POST /api/v1/admin/documents` 有接口骨架。
- `search_knowledge` 工具能返回带 `chunk_id` 的证据。

### `feat/eval-feedback`

状态：管理员端页面雏形已落地；真实评测 case、评测命令和报告接口未完成。

负责人：后端或空档同学。

范围：

- 评测 case 文件。
- 评测运行命令或接口。
- Trace 输出结构。
- 简单评测报告 JSON。

交付标准：

- 至少有 5 条 case。
- 能运行一批 case 并输出通过/失败结果。
- 每条结果关联 trace。

## 4. 分支协作规则

- `main` 保持可运行，不直接堆开发代码。
- 每个 feature 分支只负责自己的范围，避免同时改同一批文件。
- 每天至少合并一次可运行的小 PR 或小提交。
- 前后端通过接口文档和 mock 数据并行开发。
- 接口字段变更必须同步更新 `.ai/tech` 文档。
- 如果后端未完成，前端用同名 mock SSE 数据开发；后端完成后替换 API 地址。

## 5. 第一版接口契约

### 创建会话

```http
POST /api/v1/agent/sessions
```

响应：

```json
{
  "session_id": "sess_001",
  "title": "新对话"
}
```

### 流式发送消息

```http
POST /api/v1/agent/sessions/{session_id}/messages:stream
Content-Type: application/json
Accept: text/event-stream
```

请求：

```json
{
  "session_id": "sess_001",
  "client_message_id": "client_msg_001",
  "content": "预算 3000 以内，推荐一款适合拍娃的手机",
  "attachments": []
}
```

SSE：

```text
event: message_start
data: {"run_id":"run_001","session_id":"sess_001","message_id":"msg_001","trace_id":"trace_001"}

event: text_delta
data: {"delta":"预算 3000 以内拍娃，优先看对焦速度、抓拍稳定性和存储空间。"}

event: block_delta
data: {"type":"product_card","product":{"product_id":"p_001","name":"X Phone 12","price":"2999.00","image_url":"/mock/x-phone.png","tags":["预算内","拍照"],"recommend_reason":"对焦快，适合抓拍孩子。","risk_notes":["续航不是最强"]}}

event: block_delta
data: {"type":"citation","citation":{"chunk_id":"ck_001","title":"X Phone 12 商品详情","snippet":"支持高速对焦和儿童抓拍模式。"}}

event: followups
data: {"questions":["你更重视拍照还是续航？","是否需要 256GB 以上存储？"]}

event: message_end
data: {"run_id":"run_001"}
```

### 取消生成

```http
POST /api/v1/agent/runs/{run_id}:cancel
```

响应：

```json
{
  "run_id": "run_001",
  "status": "canceled"
}
```

## 6. 每日节奏

建议每天固定三次同步：

- 上午：确认今天要合并的最小目标。
- 下午：接口和联调风险同步。
- 晚上：合并可运行进展，记录第二天阻塞点。

每次同步只回答三件事：

- 今天完成了什么。
- 现在卡在哪里。
- 接下来需要谁配合。
