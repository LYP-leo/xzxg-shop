# 电商 AI 导购系统技术方案 v3

> 对应需求：[需求_v3.md](../prd/需求_v3.md)
>
> 版本目标：将当前 Web/Capacitor 演示系统迁移为 Android Studio 原生 Java APP，并补齐聊天记录存储与恢复、三角色 APP 功能、账号注册/改密/管理等能力。
>
> 当前仓库状态说明：截至本方案编写时，仓库当前分支为 `main`，实际目录包含 `backend/`、`frontend/`、`deployments/`、`quality/`，但 `android-native/` 目录在工作区处于删除状态。因此本方案按“重新建立 Android 原生端”为前提设计，不依赖已删除的 Android 代码。

## 1. 需求解读

需求 v3 的核心不是简单把 Web 页面搬到手机里，而是把系统改造成一个以 AI 聊天为主入口、同时支持顾客、商家、管理员三种角色的 Android 原生 APP。

本阶段要解决四类问题：

- 聊天记录：未登录用户本地保存，已登录用户本地保存并与服务器同步。
- 账号体系：顾客和商家可注册、改密；管理员可管理用户。
- Android 原生迁移：使用 Java + Android Studio 原生工程，不继续把 React 页面作为主客户端。
- 角色化体验：顾客、商家、管理员进入 APP 后看到不同的信息架构和功能页面。

其中“每次打开 APP 都开启一段新的聊天”是客户端体验规则，不表示历史会话丢弃。APP 启动后应创建新的当前会话，同时在后台同步历史会话摘要和最近会话详情。

## 2. 总体架构

```text
Android 原生 APP
  -> 本地数据层 Room/SQLite + SharedPreferences
  -> API Client / SSE Client
  -> Go API 服务
  -> MySQL 业务库
  -> Agent Runtime / RAG
  -> 后续 Redis / RocketMQ / Qdrant
```

职责划分：

- Android APP：负责原生交互、角色导航、本地会话缓存、后台同步、SSE 流式渲染。
- Go API：负责账号、鉴权、会话、消息、订单、商品、商家资料、管理员管理接口。
- MySQL：保存账号、商品、订单、服务端会话、服务端消息和 Agent 执行记录。
- Redis：后续用于验证码频控、登录态黑名单、分布式限流、同步锁。
- RocketMQ：后续用于文档入库、向量化、评测、会话摘要生成等异步任务。
- Qdrant：后续用于 RAG 向量检索。

技术选型：

- 语言：Java。
- UI：Android 原生 View 或 AppCompat，不使用 WebView 承载主业务。
- 网络：OkHttp + OkHttp SSE。
- JSON：Gson。
- 本地存储：Room 优先；若开发时间不足，第一阶段可用 SQLiteOpenHelper，但接口要按 Repository 抽象，避免 UI 直接读写数据库。
- 简单配置：SharedPreferences 保存 token、当前角色、测试版后端地址。

### 3.2 信息架构

APP 采用“角色化导航 + 聊天优先”的结构。顾客端参考豆包、ChatGPT 的移动端层级：主页只突出聊天，左上角抽屉承载用户管理、商品、购物车、订单和历史会话。商家端和管理员端是管理型工作台，可以继续使用底部导航或顶部 Tab，但不能和顾客聊天主页混用。

未登录默认进入顾客聊天主页：

```text
聊天主页
  -> 左侧抽屉
      -> 登录入口
      -> 商品
      -> 购物车
      -> 订单
      -> 本地历史聊天
```

未登录时可以创建本地会话、保存本地聊天记录；需要服务端 Agent、购物车、订单、个性化建议时，引导登录。

顾客登录后：

```text
聊天主页
  -> 左侧抽屉
      -> 用户头像 / 昵称 / 我的
      -> 商品
      -> 购物车
      -> 订单
      -> 历史聊天记录
      -> 右下角“聊天”按钮返回新会话主页
```

商家登录后：

```text
工作台
商品
订单
资料
我的
```

管理员：

```text
总览
用户
商品
订单
配置
```

这样拆分后，顾客端聊天页只承载导购对话；商品、购物车、订单、用户管理和历史会话从侧栏进入。商家和管理员则按 Web 端已有能力迁移为原生管理页面。

### 3.3 顾客聊天主页交互

聊天主页参考 [main.jpeg](./assets/main.jpeg) 的层级，目标是“打开即聊天”，避免用大面积菜单稀释主任务。

页面结构：

- 顶部左侧：圆形侧栏按钮，点击打开左侧抽屉。
- 顶部中间/右侧：不放复杂导航，只保留必要的同步或生成状态。
- 首屏中间：展示新会话欢迎语。
- 欢迎语下方：登录用户展示场景化建议；未登录用户不展示个性化建议，改为展示“登录以提供个性化建议”的轻提示。
- 中部消息区：发送后切换为消息流，支持文本气泡、商品卡片、引用、追问建议。
- 底部输入区：左侧加号用于添加图片；中间文字输入框；右侧语音按钮用于语音输入；生成中时右侧切换为停止按钮。

首屏欢迎语和场景化建议不能写死在 Android 端，必须由后端下发。当前后端尚未设计该接口，第一阶段先保留空占位：

```http
GET /api/v1/agent/home
```

占位响应：

```json
{
  "welcome_text": "",
  "suggestions": []
}
```

后续扩展时，后端可以根据登录状态、历史会话、购物车、订单、商品热度返回建议：

```json
{
  "welcome_text": "今天想买点什么？",
  "suggestions": [
    {
      "suggestion_id": "sg_001",
      "text": "帮我选一台 3000 元以内拍照好的手机",
      "source": "system"
    }
  ]
}
```

Android 端规则：

- 未登录：请求失败或返回空建议时，只显示欢迎语占位和登录提示，不展示伪造建议。
- 已登录：展示后端返回的建议 chips，点击后直接填入输入框或发送。
- 后端接口未完成前，Android 端只保留 UI 容器，不硬编码业务建议。

语音输入第一阶段只做入口和状态，不实现语音转文字：

- 点击语音按钮后打开录音态 UI。
- 若语音识别能力未接入，提示“语音输入能力待接入”。
- 未来通过独立 `speech` 模块接入系统语音识别或云端 ASR，输出文本后走普通发送链路。

### 3.4 顾客侧栏设计

侧栏参考 [side.jpeg](./assets/side.jpeg)，采用左侧抽屉 `DrawerLayout`。侧栏不是独立首页，而是聊天主页的导航层。

侧栏结构：

```text
用户区
  未登录：登录 / 注册按钮
  已登录：头像、昵称、账号角色，点击进入“我的”

功能入口
  商品
  购物车
  订单

历史聊天
  最近会话标题列表
  本地未同步会话标识
  点击会话后关闭抽屉并加载对应聊天

底部动作
  “聊天”按钮：回到当前新会话主页
```

用户管理页：

- 未登录：登录、注册、忘记密码。
- 已登录：头像、昵称、账号、手机号/邮箱绑定状态、修改资料、修改密码、退出登录。
- 测试版：后端地址和端口设置入口。
- 正式版：不展示后端地址设置。

顾客侧栏跳转规则：

- 商品、购物车、订单进入对应全屏页面，页面左上角提供返回聊天或打开侧栏的按钮。
- 历史会话点击后加载本地详情；若本地只有摘要，则先展示摘要骨架，再后台拉服务端详情。
- 右下角“聊天”按钮始终返回当前新会话；如果当前没有新会话则创建一个。

每次冷启动：

1. 创建一个本地新会话 `local_session_id`。
2. 如果用户已登录，后台调用服务端创建 `session_id`。
3. 新消息先写本地，再发送到服务端。
4. SSE 回来后增量更新本地助手消息。
5. `message_end` 后将消息状态改为 `completed`。

### 3.5 流式输出渲染

Android 端消费后端现有 SSE 事件：

| 事件 | Android 行为 |
| --- | --- |
| `message_start` | 建立本地助手消息和 `run_id` 绑定 |
| `status` | 展示“正在检索商品/正在生成回答”等轻提示 |
| `text_delta` | 追加到助手文本气泡 |
| `block_delta` | 根据 block 类型插入商品卡片、引用、对比表 |
| `followups` | 展示追问 chips |
| `message_end` | 标记完成，恢复输入框 |
| `error` | 标记失败，展示重试入口 |

Android 不解析模型自由文本里的商品信息。商品卡、引用、对比表必须来自 `block_delta` 的结构化字段。

### 3.6 本地数据模型

本地表：

#### local_chat_sessions

| 字段 | 说明 |
| --- | --- |
| local_session_id | 本地会话 ID |
| server_session_id | 服务端会话 ID，未同步时为空 |
| account_id | 登录用户 ID，未登录为空 |
| title | 会话标题 |
| summary | 摘要 |
| sync_state | `local_only` / `synced` / `dirty` / `failed` |
| last_message_at | 最近消息时间 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

#### local_chat_messages

| 字段 | 说明 |
| --- | --- |
| local_message_id | 本地消息 ID |
| server_message_id | 服务端消息 ID |
| local_session_id | 本地会话 ID |
| role | `user` / `assistant` / `system` |
| content | 文本内容 |
| blocks_json | 商品卡、引用、对比表等结构化块 |
| attachments_json | 图片等附件 |
| client_message_id | 幂等 ID |
| run_id | Agent run ID |
| status | `pending` / `streaming` / `completed` / `failed` / `canceled` |
| created_at | 创建时间 |
| updated_at | 更新时间 |

#### sync_jobs

| 字段 | 说明 |
| --- | --- |
| job_id | 同步任务 ID |
| job_type | `upload_message` / `download_sessions` / `download_messages` |
| payload_json | 同步参数 |
| status | `pending` / `running` / `completed` / `failed` |
| retry_count | 重试次数 |
| next_retry_at | 下次重试时间 |

### 3.7 本地优先策略

消息发送流程：

```text
用户点击发送
  -> 写 local_chat_messages(status=pending)
  -> UI 立即展示用户气泡
  -> 若未登录：保持 local_only，提示登录后可同步
  -> 若已登录：创建/确认 server_session_id
  -> POST messages:stream
  -> 收到 message_start 后绑定 server_message_id/run_id
  -> 按 text_delta/block_delta 更新本地助手消息
  -> message_end 后标记 completed
```

断网或接口失败：

- 用户消息保留在本地，状态为 `failed` 或 `pending_sync`。
- 聊天页展示重试按钮。
- 后台同步器在网络恢复后重试。

## 4. 聊天记录同步设计

### 4.1 同步目标

需求要求：

- 未登录：聊天只保存在本地。
- 已登录：本地保存，同时同步服务器。
- APP 启动时同步历史，但不能阻塞用户使用。
- 最近 50 条完整同步，更多历史只同步标题与摘要。
- 先同步近期，再同步久远；先同步标题摘要，再同步具体内容。
- 本地已有的会话不重复同步。

### 4.2 服务端接口

基于当前接口扩展：

#### 查询会话摘要

```http
GET /api/v1/agent/sessions?page=1&page_size=50&detail_mode=summary
Authorization: Bearer <token>
```

响应：

```json
{
  "items": [
    {
      "session_id": "s_001",
      "title": "帮我选手机",
      "summary": "用户预算 3000，关注拍照和续航",
      "last_message_at": "2026-05-21T10:00:00+08:00",
      "message_count": 8,
      "updated_at": "2026-05-21T10:00:00+08:00"
    }
  ],
  "next_page": 2
}
```

#### 查询会话详情

```http
GET /api/v1/agent/sessions/{session_id}?message_limit=50
```

用于同步最近 50 条完整消息。

#### 上传本地会话

```http
POST /api/v1/agent/sessions:sync
```

请求：

```json
{
  "client_session_id": "local_abc",
  "title": "本地未登录会话",
  "messages": [
    {
      "client_message_id": "cm_001",
      "role": "user",
      "content": "帮我选手机",
      "attachments": [],
      "created_at": "2026-05-21T10:00:00+08:00"
    }
  ]
}
```

服务端必须用 `client_message_id` 做幂等，避免重复上传。

### 4.3 启动同步流程

```text
APP 启动
  -> 读取本地 token
  -> 创建新的当前聊天
  -> 如果未登录：不拉服务端历史
  -> 如果已登录：启动后台同步任务
      -> 拉第一页会话摘要
      -> 本地不存在则插入摘要
      -> 对最近 50 个会话逐个拉详情
      -> 本地已有且 updated_at 未变化则跳过
      -> 更久历史只保留摘要
```

同步任务必须在后台执行，聊天输入和页面切换不能被阻塞。

### 4.4 同步冲突规则

- 同一条消息以 `client_message_id` 为准。
- 服务端已有同 `client_message_id` 时，客户端不重复插入。
- 服务端内容为权威记录，但本地 `pending` 消息不能被删除，只能在上传成功后变更状态。
- 如果同一会话本地和服务端标题不同，以服务端标题为准，本地可保留 `local_title_override` 作为后续扩展。

## 5. 后端改造设计

### 5.1 账号与验证码

新增接口：

```http
POST /api/v1/auth/verification-codes
POST /api/v1/auth/register
POST /api/v1/auth/password:change
POST /api/v1/auth/password:reset
```

验证码第一阶段设计：

- 不自建真正邮件服务器和短信网关。
- 后端抽象 `verification.Sender` 接口。
- 开发环境使用 mock sender，把验证码写入日志或测试表。
- 生产/比赛演示环境预留云服务实现，例如阿里云短信、腾讯云短信、SendCloud、阿里云邮件推送。

验证码表：

| 字段 | 说明 |
| --- | --- |
| code_id | 验证码记录 ID |
| scene | `register` / `reset_password` / `change_password` |
| target_type | `phone` / `email` |
| target | 手机号或邮箱 |
| code_hash | 验证码哈希 |
| status | `unused` / `used` / `expired` |
| expires_at | 过期时间 |
| created_at | 创建时间 |

Redis 接入后用于：

- 同一手机号/邮箱 60 秒内只能发送一次。
- 同一 IP 每小时发送次数限制。
- 验证码错误次数限制。

### 5.2 用户注册

顾客注册：

```http
POST /api/v1/auth/register
```

```json
{
  "role": "user",
  "username": "leo",
  "password": "******",
  "display_name": "Leo",
  "target_type": "email",
  "target": "leo@example.com",
  "verification_code": "123456"
}
```

商家注册：

```json
{
  "role": "merchant",
  "username": "shop_owner",
  "password": "******",
  "display_name": "小猪店主",
  "merchant_name": "小猪数码店",
  "target_type": "phone",
  "target": "13800000000",
  "verification_code": "123456"
}
```

商家注册时创建 `merchants` 记录，并将账号 `merchant_id` 绑定到新商家。

### 5.3 密码修改与重置

已登录修改密码：

```http
POST /api/v1/auth/password:change
```

```json
{
  "old_password": "old",
  "new_password": "new"
}
```

忘记密码重置：

```http
POST /api/v1/auth/password:reset
```

```json
{
  "target_type": "email",
  "target": "leo@example.com",
  "verification_code": "123456",
  "new_password": "new"
}
```

### 5.4 管理员用户管理

当前已有账号列表和启停接口，需要扩展：

```http
POST /api/v1/admin/accounts
PATCH /api/v1/admin/accounts/{account_id}
POST /api/v1/admin/accounts/{account_id}/password:reset
```

管理员可执行：

- 查看顾客、商家、管理员账号。
- 启用/停用账号。
- 创建管理员或商家账号。
- 重置用户密码。
- 查看商家绑定关系。

### 5.5 用户资料管理

顾客侧栏顶部和“我的”页面需要可编辑用户资料。资料接口与登录态绑定，只允许操作当前账号。

查询资料：

```http
GET /api/v1/account/profile
```

响应：

```json
{
  "account_id": "a_001",
  "username": "leo",
  "role": "user",
  "nickname": "Leo",
  "avatar_url": "",
  "phone": "",
  "email": "leo@example.com",
  "phone_verified": false,
  "email_verified": true
}
```

修改资料：

```http
PATCH /api/v1/account/profile
```

```json
{
  "nickname": "Leo",
  "avatar_url": ""
}
```

资料修改边界：

- 第一阶段只允许修改昵称和头像 URL。
- 手机号、邮箱变更必须走验证码校验，不能直接 PATCH。
- 用户名作为登录账号，第一阶段不允许修改。
- 侧栏用户区读取 `nickname`，为空时回退到 `display_name` 或 `username`。

## 6. 三角色 APP 功能设计

### 6.1 顾客端

顾客端以聊天主页为中心，其他页面从侧栏进入。

页面：

- 聊天主页：欢迎语、场景化建议、流式输出、商品卡片、引用、追问、图片入口、语音入口。
- 侧栏：登录/用户管理入口、商品、购物车、订单、历史聊天、返回聊天按钮。
- 商品：商品列表、搜索筛选、商品详情、SKU、加入购物车。
- 购物车：商品选中、数量修改、删除、结算。
- 订单：订单列表、订单详情、状态展示。
- 我的：登录、注册、忘记密码、修改资料、修改密码、退出登录。

核心链路：

```text
打开 APP -> 新建聊天 -> 输入需求 -> 流式推荐 -> 商品卡加入购物车 -> 购物车下单 -> 订单列表
```

视觉要求：

- 风格现代、简洁、统一，优先白底、低噪音、充足留白。
- 聊天页只放高频聊天控件，不把商品、购物车、订单模块塞到聊天页。
- 商品卡片在聊天流中紧凑展示，点击进入商品详情。
- 页面动线必须稳定：侧栏负责全局导航，聊天按钮负责回到主聊天。

### 6.2 商家端

商家端参考当前 Web 商家页能力，但改成移动端工作台，不复用顾客聊天侧栏。

页面：

- 工作台：订单概览、商品数量、资料状态。
- 商品：列表、搜索、查看、新增、编辑、删除、上下架、库存。
- 订单：待发货、已发货、已完成，支持发货操作。
- 资料：上传商品详情、营销文档，查看知识库处理状态和 chunk 数。
- 我的：店铺信息、账号设置、改密。

移动端设计：

- 工作台用数据摘要卡展示今日订单、待发货、商品数量、资料数量。
- 商品列表用可扫读行项目，不做复杂表格。
- 商品编辑使用分组表单：基础信息、价格库存、标签卖点、风险提示。
- 文档上传页先支持文本粘贴/输入，后续再接文件上传。

商家资料上传流程：

```text
商家提交文档
  -> 后端保存 knowledge_documents
  -> 第一阶段同步切片写 knowledge_chunks
  -> 后续通过 RocketMQ 异步解析、切片、Embedding、写 Qdrant
```

### 6.3 管理员端

管理员端参考当前 Web 管理页能力，移动端采用管理列表 + 详情编辑的结构。

页面：

- 总览：用户、商品、订单、知识库、模型配置概览。
- 用户：账号列表、启停、创建、重置密码。
- 商品：商品审核、下架。
- 订单：全平台订单查看。
- 配置：模型、Prompt、开关、验证码 provider 配置。

管理员端不进入普通导购聊天作为默认首页，避免和运营管理工作流混淆。

移动端设计：

- 列表页提供搜索、角色/状态筛选、分页加载。
- 用户详情页展示账号、角色、状态、绑定联系方式、商家关系。
- 配置页对密钥类字段只展示掩码，修改时二次确认。
- 管理操作必须有确认弹窗，避免误停用账号或误下架商品。

## 8. 数据库变更

新增或调整表：

```text
verification_codes
account_contacts
account_profiles 或扩展 accounts 字段
assistant_messages
chat_session_summaries 或扩展 chat_sessions 字段
```

### 8.1 account_contacts

用于绑定邮箱和手机号。

| 字段 | 说明 |
| --- | --- |
| contact_id | 主键 |
| account_id | 账号 ID |
| target_type | `phone` / `email` |
| target | 手机号或邮箱 |
| verified | 是否已验证 |
| created_at | 创建时间 |

### 8.2 assistant_messages

用于保存助手最终消息，支撑历史恢复。

| 字段 | 说明 |
| --- | --- |
| assistant_message_id | 助手消息 ID |
| session_id | 会话 ID |
| user_message_id | 对应用户消息 |
| run_id | Agent 执行 ID |
| account_id | 用户账号 ID |
| content | 最终文本 |
| blocks_json | 结构化块 |
| status | `streaming` / `completed` / `failed` / `canceled` |
| created_at | 创建时间 |
| updated_at | 更新时间 |

当前 `user_messages` 只保存用户消息，恢复完整聊天还需要保存助手消息，否则历史页只能看到用户提问和 run 信息，无法完整还原聊天体验。

### 8.3 account_profiles

用于支持 APP “我的”页面和侧栏用户区。

| 字段 | 说明 |
| --- | --- |
| account_id | 账号 ID |
| avatar_url | 头像 |
| nickname | 昵称 |
| bio | 简介，可选 |
| updated_at | 更新时间 |

如果开发时间有限，也可以先扩展 `accounts` 表的 `display_name`，头像使用默认图；但接口层仍按 profile 契约设计。

### 8.4 chat_sessions 扩展

建议增加：

```sql
summary TEXT,
last_message_at DATETIME,
message_count INT NOT NULL DEFAULT 0,
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

这些字段用于启动同步时先展示标题和摘要。

## 11. 风险与边界

- 当前 `android-native/` 已不在工作区，需要先重建原生工程。
- 当前服务端历史恢复缺少助手消息表，必须补齐，否则 Android 历史页无法完整展示 AI 回复。
- 手机验证码和邮箱验证码不建议自建真实发送服务，第一阶段使用 mock，后续接云服务。
- Android 原生 UI 不能简单照搬 Web，需要按移动端信息架构重新设计；顾客端以聊天主页和侧栏为核心。
- 欢迎语和场景化建议必须来自后端，Android 端不能硬编码业务建议。
- 语音输入第一阶段只做入口，ASR 方案后续单独设计。
- RAG、Qdrant、RocketMQ 可以与 Android 迁移并行，但本阶段不应阻塞聊天主链路。
