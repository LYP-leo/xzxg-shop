# 编码规范 v1

## 1. 基本原则

本仓库用于比赛项目，代码应优先服务于可演示、可评测、可维护。所有实现遵循以下原则：

- 业务逻辑清晰优先于过度抽象。
- 关键链路必须有日志、错误处理和可追踪信息。
- 大模型输出不可直接信任，必须经过结构化解析、校验和降级处理。
- 商品价格、库存、活动规则、售后政策等关键事实必须来自数据库或知识库证据。
- 前后端接口以稳定契约为中心，不让 UI 直接依赖模型自由文本。

## 3. 目录规范

推荐目录：

```text
backend/
  cmd/
  src/
  prompts/
  migrations/
frontend/
  src/
deployments/
.ai/
  prd/
  tech/
  pics/
```

规则：
- `.ai/prd` 只放需求文档。
- `.ai/tech` 放技术方案、接口设计、编码规范、测试方案。
- `.ai/pics` 放架构图、流程图、参考图。
- 后端业务代码放 `backend/src`，避免散落在根目录。
- 前端源码放 `frontend/src`。

## 4. Go 后端规范

### 4.1 包命名

- 包名使用小写单词，不使用下划线。
- 包名表达职责，例如 `handler`、`service`、`repository`、`agent`。
- 不使用 `common`、`utils` 承载大量无关逻辑。确实通用的能力按职责命名，例如 `xerrors`、`datetime`。

### 4.2 分层规范

推荐调用方向：

```text
handler -> service -> repository
handler -> service -> agent -> llm/vector/product service
```

要求：
- `handler` 只做参数绑定、鉴权上下文、响应封装，不写复杂业务。
- `service` 编排业务流程。
- `repository` 只负责数据访问。
- `agent` 负责 Prompt、工具调用、RAG 编排和结构化输出。
- `llm` 封装模型供应商细节。
- `vector` 封装向量数据库细节。

### 4.3 命名规范

- 导出类型和函数使用 `PascalCase`。
- 非导出变量和函数使用 `camelCase`。
- 常量按业务语义命名，避免魔法字符串散落。
- ID 字段统一使用 `ID` 后缀，例如 `ProductID`、`SessionID`。

示例：

```go
type ChatMessage struct {
    ID        int64
    SessionID int64
    Role      MessageRole
    Content   string
}
```

### 4.4 Context 规范

- 所有外部 IO 函数必须接收 `context.Context`。
- HTTP 请求的 context 必须向下传递到 DB、Redis、LLM、向量库。
- 不在函数内部创建无超时的 `context.Background()` 调用外部服务。

### 4.5 错误处理

- 错误必须返回，不吞掉。
- 对外响应使用统一错误码。
- 内部错误使用 `%w` 包装，保留根因。
- 日志记录时带上 `request_id`、`session_id`、`message_id` 等关键字段。

示例：

```go
if err != nil {
    return fmt.Errorf("search knowledge chunks: %w", err)
}
```

### 4.6 日志规范

必须记录：
- 请求入口和结束。
- Agent 每个关键步骤耗时。
- LLM 调用模型、耗时、token、错误。
- RAG Query、Top-K 数量、命中 chunk ID。
- 异步任务开始、结束、失败原因。

禁止：
- 日志中输出完整密钥。
- 默认输出用户上传图片的原始内容。
- 大量输出完整 Prompt 和完整文档内容。需要排查时用 debug 开关。

### 4.7 数据库规范

- 所有表必须包含 `created_at`，需要更新的表包含 `updated_at`。
- 软删除仅在确有恢复需求时使用。
- 外键关系在应用层也要校验，不完全依赖数据库约束。
- 常用查询字段必须建索引，例如 `session_id`、`message_id`、`document_id`、`product_id`。
- JSON 字段用于灵活扩展，不用于频繁条件查询的核心字段。

### 4.8 API 规范

- API 前缀统一为 `/api/v1`。
- 使用 JSON 作为默认请求响应格式。
- 列表接口统一支持 `page`、`page_size`。
- 创建类接口返回资源 ID。
- 幂等写入使用客户端传入的 `client_message_id` 或业务唯一键。
- SSE 接口事件类型必须稳定，不随意改名。

### 4.9 大模型调用规范

- 所有模型调用必须通过 `src/llm` 封装。
- Prompt 必须有版本号。
- 结构化输出必须做 JSON Schema 或 Go struct 校验。
- 模型超时必须设置。
- 模型返回不合法时最多重试一次，并记录失败。
- 关键事实不能只依赖模型生成。

## 5. React 前端规范

### 5.1 技术约定

- 使用 TypeScript。
- 组件使用函数组件。
- 网络请求集中在 `src/api`。
- 业务类型集中在 `src/types`。
- 页面级组件放 `src/pages`。
- 可复用 UI 放 `src/components`。

### 5.2 组件规范

- 单个组件只承担一个主要职责。
- 对话消息、商品卡片、对比表、引用来源拆成独立组件。
- 组件 props 必须有明确 TypeScript 类型。
- 不在组件里硬编码复杂数据转换逻辑，转换逻辑放到 helper 或 store。

### 5.3 状态管理

- 页面局部状态使用 `useState`、`useReducer`。
- 跨组件共享状态使用 Zustand 或 Context。
- SSE 消息流状态必须支持：
  - 追加文本 delta。
  - 插入商品卡片。
  - 插入引用来源。
  - 标记完成、失败、取消。

### 5.4 UI 规范

- 对话页优先服务高频使用，不做无关营销页。
- 商品卡片信息要紧凑、可扫读。
- 商品价格、库存、活动标签必须有明确视觉层级。
- AI 回复中的引用来源应可展开查看。
- 加载、失败、空状态都必须有明确表现。
- 移动端布局优先，桌面端自适应。

### 5.5 网络与错误处理

- 所有 API 错误统一转为用户可理解的提示。
- SSE 断开时展示重试入口。
- 用户点击停止生成后前端要立即更新状态，并调用后端取消接口。
- 上传图片前校验类型和大小。

## 6. 接口契约规范

请求字段：
- JSON 字段使用 `snake_case`。
- 时间使用 RFC3339 字符串。
- 金额后端可使用 decimal 字符串返回，避免浮点误差。
- ID 对前端统一作为字符串处理，避免 JavaScript 大整数精度问题。

响应字段：
- 成功响应直接返回业务 data，或使用统一 envelope。项目内必须保持一致。
- 错误响应包含 `code`、`message`、`request_id`。

SSE 事件：
- 事件名使用 `snake_case`。
- 每个事件 data 必须是合法 JSON。
- `message_start` 和 `message_end` 必须成对出现；异常时发送 `error`。

## 7. Prompt 与评测规范

Prompt 文件：
- 存放在 `backend/prompts`。
- 文件名包含用途和版本，例如 `rag_answer_v1.md`。
- 修改 Prompt 必须说明原因，并尽量关联评测结果。

评测 Case：
- 每个核心场景至少有 3 到 5 条 Case。
- Case 应包含用户输入、期望要点、期望商品或期望引用。
- 多轮 Case 必须明确每轮用户约束变化。

评测报告：
- 记录模型版本、Prompt 版本、知识库版本。
- 记录准确率、检索命中率、商品命中率、格式合规率。
- 保留失败样例和失败原因。

## 8. 项目交付补充规范

### 8.1 目录结构

项目按端和职责拆分目录：

```text
backend/          Go 服务端代码、数据库迁移、Prompt 和服务配置
frontend/         React Web/Capacitor 客户端代码
android-native/   Kotlin Android 原生客户端代码
quality/          测评脚本、测评 case、RAG/Agent 数据集
deployments/      Docker Compose 与生产化中间件配置
.ai/              PRD、技术方案、编码规范、测试记录
```

新增代码必须放入对应目录，不在仓库根目录散落业务实现。

### 8.2 依赖管理

- Go 依赖统一维护在 `backend/go.mod` 和 `backend/go.sum`。
- React 依赖统一维护在 `frontend/package.json` 和 `frontend/package-lock.json`。
- Android 原生依赖统一维护在 `android-native/build.gradle` 与 `android-native/app/build.gradle`。
- Docker 中间件版本统一维护在 `deployments/docker-compose.yml`。
- 新增依赖必须说明用途，避免引入只服务单个小函数的大型库。

### 8.3 注释要求

- RAG 检索、Prompt 构造、Agent 工具调用、SSE 流式输出等核心链路需要保留简短注释说明边界和关键约束。
- 注释解释“为什么这样做”，不要重复代码字面含义。
- 涉及模型安全边界时，注释应明确事实来源、降级策略和禁止编造的字段。

### 8.4 代码结构与接口质量

- 接口设计要保持稳定契约，前端优先消费结构化字段和 block，不直接解析大模型自由文本。
- 错误响应必须包含稳定 `code`、可读 `message` 和 `request_id`。
- Agent 执行购物车、下单等真实业务动作时，必须先经过后端工具层校验，不能只让模型口头声称已完成。
- 质量测评 case 要随核心功能同步维护，新增能力至少补 1 条正常 case 和 1 条边界/失败 case。

## 8. 测试规范

后端测试：
- Service 和 Agent 工具函数优先写单元测试。
- Repository 可用集成测试覆盖关键查询。
- RAG 检索和评测链路至少保留可复现的测试数据。

前端测试：
- 商品卡片、对比表、SSE 消息 reducer 建议优先测试。
- 复杂 UI 状态必须覆盖加载、成功、失败、取消。

手工验收：
- 文档上传后能检索。
- 用户问商品参数，回答能引用来源。
- 用户问推荐，能输出商品卡片。
- 用户问对比，能输出对比表。
- 图片上传后，Agent 能使用解析结果回答。
- 评测集能运行并输出报告。

## 9. 安全规范

- `.env` 不提交仓库。
- API Key、数据库密码、模型密钥只通过环境变量注入。
- 上传文件必须校验 MIME、大小和扩展名。
- 用户输入进入 Prompt 前需控制长度。
- 管理接口必须预留鉴权能力，即使 MVP 阶段使用简单 token。
- 日志和评测样例避免包含真实手机号、地址、身份证等隐私。

## 10. 代码质量要求

提交前至少执行：

后端：

```bash
go fmt ./...
go test ./...
```

前端：

```bash
npm run lint
npm run build
```

如果命令暂未配置，需要在 PR 或提交说明里明确未执行原因。

## 11. 文档维护规范

- 需求变化先更新 `.ai/prd`。
- 技术方案变化更新 `.ai/tech`。
- 架构图和流程图放 `.ai/pics`。
- 重要决策应在技术文档中留下取舍原因。
- 接口字段变更必须同步更新技术方案或接口文档。

## 12. 禁止事项

- 禁止把模型返回的商品价格、库存、活动规则直接当作事实写入前端。
- 禁止在无检索证据时输出确定性政策或参数。
- 禁止在业务代码中散落模型 API Key。
- 禁止忽略异步任务失败。
- 禁止在前端只渲染自由文本而丢弃结构化商品卡片。
- 禁止为了演示写死核心问答结果；可以使用 mock 商品数据，但链路必须真实可运行。
