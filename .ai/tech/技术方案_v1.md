# 电商 AI 导购系统技术方案 v1

## 1. 方案目标

本方案基于 PRD v1，定义比赛项目第一版工程实现方案。系统采用 React 客户端、Go 后端、MySQL、Redis、RocketMQ、向量数据库、大模型 OpenAPI 和 Docker 部署，覆盖“商品资料上传 - 知识库构建 - 意图理解 - RAG 咨询 - 商品推荐 - 流式交互 - 质量评测反馈”的完整链路。

第一版目标不是追求复杂商业电商闭环，而是优先完成比赛可演示、可评测、可解释的 AI 导购核心能力：

- 用户能通过文字/图片发起导购咨询。
- Agent 能识别意图、澄清需求、检索知识、推荐商品并给出决策理由。
- 客户端能流式展示文本，并实时渲染商品卡片、对比表和引用来源。
- 运营能上传商品详情与营销文档，构建专属知识库。
- 研发能运行评测集，量化回答准确率、检索命中率和多轮逻辑表现。

## 2. 技术栈

客户端：
- React + TypeScript。
- 状态管理优先使用轻量方案，例如 Zustand 或 React Context。
- 网络请求使用 Fetch，流式对话使用 SSE；如后续需要双向实时能力再引入 WebSocket。

后端：
- Go 1.22+。
- HTTP 框架建议 Gin 或 go-chi，第一版优先选择 Gin，便于快速交付。
- ORM 建议 GORM；复杂查询可退回原生 SQL。
- 配置管理使用环境变量 + YAML 配置文件。

中间件：
- MySQL：业务主库，存储商品、会话、文档、评测、反馈等结构化数据。
- Redis：会话短期记忆、SSE 状态、限流、热点数据缓存、分布式锁。
- RocketMQ：文档解析、Embedding、评测任务等异步任务。
- 向量数据库：建议 Milvus、Qdrant 或 pgvector。第一版优先 Qdrant，部署轻量、API 简单、适合比赛演示。

AI 能力：
- Chat Model OpenAPI：用于意图理解、导购问答、推荐解释、评测评分。
- Embedding OpenAPI：用于知识片段向量化和 Query 向量化。
- Vision/OCR OpenAPI：用于图片商品图、活动海报、购物车截图解析。

部署：
- Docker Compose 本地一键启动。
- 服务包括 frontend、api、worker、mysql、redis、rocketmq、qdrant。

## 3. 总体架构

系统分为四层：

1. 客户端交互层
   - 对话页面。
   - 图片上传。
   - 流式消息渲染。
   - 商品卡片、商品对比、引用来源组件。

2. API 与 Agent 编排层
   - 用户鉴权与会话管理。
   - 消息接入与 SSE 流式响应。
   - 意图识别、Query 改写、记忆读取、工具调用、答案生成。
   - UI 结构化事件输出。

3. 知识与商品能力层
   - 文档解析与切片。
   - Embedding 与向量检索。
   - 商品检索、筛选、排序、对比。
   - 营销规则与售后政策检索。

4. 评测与反馈层
   - 评测集管理。
   - 批量评测执行。
   - 自动评分和人工标注。
   - Prompt/知识库优化建议沉淀。

## 4. 服务划分

### 4.1 frontend

职责：
- 提供用户侧 AI 导购页面。
- 提供运营/研发管理页面的轻量版本。
- 处理 SSE 事件流并按事件类型渲染。

主要模块：
- `chat`：会话列表、消息列表、输入框、图片上传、停止生成。
- `components/product-card`：商品卡片。
- `components/product-compare`：商品对比表。
- `components/citation-list`：引用来源展示。
- `admin/documents`：文档上传和处理状态。
- `admin/evaluation`：评测集与评测报告。

### 4.2 api

职责：
- 对外提供 HTTP API。
- 承载同步业务流程和 SSE 流式对话。
- 发起 RocketMQ 异步任务。
- 调用 Agent Service、Product Service、Knowledge Service、Evaluation Service。

建议内部包：
- `internal/app`：应用启动、路由注册、依赖注入。
- `internal/config`：配置加载。
- `internal/handler`：HTTP Handler。
- `internal/service`：业务服务。
- `internal/repository`：MySQL 数据访问。
- `internal/agent`：Agent 编排、工具定义、Prompt。
- `internal/llm`：大模型、Embedding、Vision 客户端。
- `internal/vector`：向量数据库客户端。
- `internal/mq`：RocketMQ 生产与消费封装。
- `internal/sse`：流式事件封装。
- `internal/domain`：领域对象和枚举。

### 4.3 worker

职责：
- 消费异步任务。
- 执行文档解析、知识切片、Embedding、向量入库。
- 执行批量评测。
- 执行会话后处理，例如摘要、失败样例归因。

第一版可以与 `api` 共用同一份 Go 代码，通过不同启动命令区分：
- `api server`
- `api worker`

## 5. Agent 主链路设计

参考 `.ai/pics/参考-agent主链路.png`，第一版 Agent 采用“主 Agent + 工具调用 + 流式事件”的架构，不强依赖复杂多 Agent 框架，但保留扩展点。

### 5.1 主流程

1. 请求入口
   - 校验用户、会话、消息参数。
   - 基于 Redis 做限流。
   - 创建用户消息记录。

2. 上下文初始化
   - 从 MySQL 读取最近 N 条消息。
   - 从 Redis 读取会话短期记忆。
   - 如有图片，先调用图片解析工具。

3. Query 改写与记忆整理
   - 对用户原始输入、历史上下文、图片解析结果进行 Query 改写。
   - 抽取用户偏好，例如预算、使用场景、品牌倾向、排除项。

4. 意图识别
   - 分类为商品推荐、商品对比、参数咨询、优惠规则、售后咨询、图片解析、闲聊兜底等。
   - 输出是否需要澄清。

5. 工具调用规划
   - RAG 检索：查商品详情、营销规则、售后政策、FAQ。
   - 商品检索：按类目、品牌、价格、标签、库存筛商品。
   - 商品对比：整理核心属性差异。
   - 视觉解析：处理图片输入。

6. 答案生成
   - 基于检索证据、商品数据和用户偏好生成回答。
   - 严格要求关键参数、价格、活动规则来自证据或商品服务。
   - 知识不足时明确说明不确定。

7. UI 事件输出
   - 通过 SSE 输出文本 token。
   - 输出商品卡片事件、对比表事件、引用来源事件、追问建议事件。

8. 会话后处理
   - 保存助手消息。
   - 保存检索日志、工具调用日志、Prompt 版本。
   - 异步生成会话摘要并更新 Redis/MySQL。

### 5.2 意图枚举

```text
product_recommendation  商品推荐
product_comparison      商品对比
product_attribute_qa    商品参数咨询
promotion_qa            优惠与营销规则咨询
after_sales_qa          售后政策咨询
image_understanding     图片解析咨询
clarification           澄清追问
general_chat            通用闲聊
fallback                兜底
```

### 5.3 Agent 工具

第一版内置工具：

- `rewrite_query`：结合上下文改写 Query。
- `classify_intent`：识别意图和缺失槽位。
- `search_knowledge`：RAG 检索知识片段。
- `search_products`：商品结构化筛选。
- `compare_products`：商品属性对比。
- `parse_image`：图片 OCR/视觉理解。
- `generate_answer`：答案生成。
- `evaluate_answer`：评测场景下自动评分。

工具调用由 Go 代码显式编排，LLM 主要负责理解、生成和结构化输出，避免第一版过度依赖模型自主工具调用造成不可控。

## 6. RAG 方案

### 6.1 文档类型

支持上传：
- 商品详情文档。
- 营销活动文档。
- 售后政策文档。
- FAQ。
- 导购话术。
- 图片类文档，先 OCR 后入库。

### 6.2 处理流程

1. 上传文档到本地对象存储目录或 MinIO 兼容存储。
2. 写入 `documents` 表，状态为 `uploaded`。
3. 投递 `document.parse` 消息。
4. Worker 解析文档文本，状态改为 `parsed`。
5. 清洗文本，去除页眉页脚、重复空白、无意义噪声。
6. 按语义和商品维度切片，写入 `knowledge_chunks`。
7. 投递 `document.embed` 消息。
8. Worker 生成 Embedding，写入向量数据库。
9. 更新文档状态为 `indexed`。

### 6.3 切片策略

第一版默认策略：
- 每个 chunk 约 500 到 800 中文字符。
- overlap 约 80 到 120 字符。
- 表格按行组或主题块保留，不强行截断。
- 商品参数、活动规则、售后政策必须保留标题和来源元数据。

chunk 元数据：
- `document_id`
- `document_type`
- `product_id`
- `category`
- `brand`
- `source_page`
- `effective_start`
- `effective_end`
- `version`

### 6.4 检索策略

检索流程：
1. 根据意图生成检索 Query。
2. 对 Query 生成 Embedding。
3. 根据类目、商品 ID、文档类型、有效期做过滤。
4. 向量 Top-K 检索，默认 K=8。
5. 可选关键词召回，补充精确参数和规则词。
6. 重排，优先保留与商品、规则、用户问题强相关片段。
7. 传入 LLM 的证据片段控制在 token 预算内。

无证据策略：
- 商品关键参数无证据时不回答确定值。
- 活动规则无证据时提示需要以页面实际规则为准。
- 售后政策无证据时建议查看官方政策或转人工。

## 7. 流式交互协议

第一版使用 SSE。

接口：

```http
POST /api/v1/chat/sessions/{session_id}/messages:stream
Content-Type: application/json
Accept: text/event-stream
```

请求：

```json
{
  "client_message_id": "uuid",
  "content": "预算3000以内，想买适合拍娃的手机",
  "attachments": [
    {
      "attachment_id": "att_001",
      "type": "image",
      "url": "https://example.com/a.png"
    }
  ]
}
```

SSE 事件：

```text
event: message_start
data: {"message_id":"msg_001","session_id":"sess_001"}

event: text_delta
data: {"delta":"我会优先考虑对焦速度、"}

event: product_cards
data: {"products":[{"product_id":"p_001","name":"X Phone 12","price":"2999.00","reason":"拍照对焦快，预算内"}]}

event: comparison_table
data: {"columns":["商品","优势","短板"],"rows":[["X Phone 12","拍照好","续航一般"]]}

event: citations
data: {"citations":[{"chunk_id":"ck_001","title":"手机商品详情","snippet":"..."}]}

event: followups
data: {"questions":["更重视拍照还是续航？","是否需要大存储？"]}

event: message_end
data: {"message_id":"msg_001","usage":{"input_tokens":1200,"output_tokens":450}}

event: error
data: {"code":"llm_timeout","message":"模型响应超时，请稍后重试"}
```

客户端渲染规则：
- `text_delta` 追加到当前助手消息。
- `product_cards` 渲染商品卡片区，允许在文本未结束时先出现。
- `comparison_table` 渲染对比表。
- `citations` 渲染引用来源。
- `followups` 渲染追问建议。
- `message_end` 标记消息完成。

## 10. 异步流程

### 10.1 RocketMQ Topic

| Topic | 生产者 | 消费者 | 说明 |
| --- | --- | --- | --- |
| document.parse | api | worker | 文档解析 |
| document.embed | worker | worker | 片段 Embedding 与向量入库 |
| eval.run | api | worker | 批量评测 |
| chat.postprocess | api | worker | 会话摘要、Trace 分析 |

### 10.2 文档解析异步流程

```text
API 上传文档
  -> MySQL documents.status = uploaded
  -> 发送 document.parse
Worker 消费 document.parse
  -> documents.status = parsing
  -> 解析文件，抽取文本和元数据
  -> 切片，写 knowledge_chunks
  -> documents.status = parsed
  -> 发送 document.embed
Worker 消费 document.embed
  -> documents.status = indexing
  -> 为 chunk 生成 embedding
  -> 写入 Qdrant
  -> 更新 vector_id 和 chunk.status
  -> documents.status = indexed
```

失败处理：
- 每个消息最多重试 3 次。
- 超过重试次数后状态改为 `failed`。
- 错误写入 `documents.error_message`。
- 管理后台允许手动重新解析或重新索引。

### 10.3 评测异步流程

```text
API 创建 eval_run
  -> eval_runs.status = pending
  -> 发送 eval.run
Worker 消费 eval.run
  -> eval_runs.status = running
  -> 逐个执行 eval_case
  -> 调用同一套 Agent 链路，但标记 evaluation_mode = true
  -> 记录回答、检索结果、工具调用日志
  -> 自动评分
  -> 写 eval_results
  -> 聚合 metrics_json
  -> eval_runs.status = completed
```

评分维度：
- 回答准确率：是否覆盖标准答案要点。
- 检索命中率：Top-K 是否命中期望 chunk。
- 商品命中率：推荐商品是否符合期望。
- 格式合规率：是否输出商品卡片、引用、追问等结构化字段。
- 多轮一致性：是否正确继承上文约束。

### 10.4 会话后处理异步流程

```text
流式回答完成
  -> 保存 assistant message
  -> 发送 chat.postprocess
Worker 消费 chat.postprocess
  -> 生成/更新会话摘要
  -> 提取用户长期偏好候选
  -> 分析失败风险，例如无引用、低置信度
  -> 写 agent_trace_logs 或优化建议
```

## 11. Prompt 策略

### 11.1 Prompt 版本管理

Prompt 以文件形式保存在后端仓库，例如：

```text
backend/prompts/
  intent_v1.md
  rewrite_query_v1.md
  rag_answer_v1.md
  eval_judge_v1.md
```

每次模型调用记录：
- prompt name
- prompt version
- model
- temperature
- input hash
- output

### 11.2 答案生成原则

系统 Prompt 必须约束：
- 不编造商品参数、价格、库存、优惠规则。
- 关键结论必须来自商品服务或知识片段。
- 推荐必须包含适合人群、不适合情况、风险提示。
- 信息不足时先追问。
- 用户需求冲突时明确指出冲突并给出取舍建议。
- 输出结构化 JSON 供服务端解析，再转换为 SSE 事件。

## 12. 缓存与限流

Redis Key 设计：

```text
rate:user:{user_id}:chat                用户对话限流
session:{session_id}:memory             会话短期记忆
stream:{message_id}:status              SSE 状态
lock:document:{document_id}:index        文档索引锁
product:detail:{product_id}             商品详情缓存
```

限流策略：
- 普通用户每分钟最多 10 次对话请求。
- 文档上传按用户和文件大小限制。
- 评测任务限制并发，避免耗尽模型额度。

## 13. 错误处理

错误码：

| code | 说明 |
| --- | --- |
| ok | 成功 |
| invalid_argument | 参数错误 |
| unauthenticated | 未登录 |
| permission_denied | 无权限 |
| not_found | 资源不存在 |
| rate_limited | 触发限流 |
| llm_error | 大模型调用失败 |
| vector_error | 向量库调用失败 |
| document_parse_failed | 文档解析失败 |
| internal_error | 系统错误 |

Agent 降级：
- RAG 失败：提示当前知识检索不可用，不输出确定性参数。
- 商品服务失败：继续回答通用知识，但不渲染商品卡片。
- LLM 超时：中断 SSE 并返回可重试错误。
- 图片解析失败：提示图片无法识别，用户可补充文字。

## 14. 可观测性

日志：
- 每个请求生成 `request_id`。
- Agent 每一步写 trace log。
- LLM 调用记录耗时、token、模型、错误码。
- 向量检索记录 Query、Top-K、分数。

指标：
- API P50/P95/P99 延迟。
- 首 token 延迟。
- SSE 中断率。
- 文档处理成功率。
- 检索命中率。
- 评测通过率。
- LLM 调用失败率与成本。

## 17. MVP 开发顺序

3. 实现文档上传、解析、切片和 Qdrant 入库。
4. 实现知识库检索调试接口。
5. 实现聊天会话、消息存储和 SSE 流式输出。
6. 实现 Agent v1：意图识别、RAG 检索、商品检索、答案生成。
7. 实现前端对话页、商品卡片、引用来源和对比表。
8. 实现图片上传与 OCR/视觉解析。
9. 实现评测集、批量评测和评测报告。
10. 根据评测结果优化 Prompt、切片和检索参数。

## 18. 第一版取舍

保留：
- 工程链路完整性。
- RAG 可解释性。
- 流式体验。
- 商品卡片和对比。
- 质量评测闭环。

暂缓：
- 真实支付下单。
- 复杂权限系统。
- 多商家多租户。
- 完整推荐算法平台。
- 复杂多 Agent 自主规划框架。

第一版的核心标准是：评委能看到一个可运行、可解释、可评测的 AI 导购工程闭环。
